# CollegePortal

Информационная система колледжа искусств: приёмная комиссия, контингент, учебные планы, нагрузка, расписание, электронный журнал, кадры, проходная по QR, отчёты, подготовка данных для ФИС ГИА и ФРДО.

Стек: Laravel 12 / PHP 8.4 / PostgreSQL 17 / Redis на бэкенде, Vue 3 + Vite + Pinia + Quasar на фронтенде, Docker Compose и Nginx в развёртывании.

## Язык

Ответы пользователю, планы, отчёты, документация и любой текст интерфейса — на русском. Английский только для неизменяемых технических идентификаторов: команды, пути, URL, endpoints, имена классов и переменных, ветки и сообщения коммитов.

## Главное, что нужно знать до начала работы

**На рабочей станции Windows нет инструментов разработки.** Ни `php`, ни `node`, ни `npm`, ни `docker`, ни `composer`. Есть только `git`, `ssh` и VS Code. Не пытайтесь запускать здесь тесты или сборку — это не поломка, так устроено рабочее место.

Вся сборка и все проверки выполняются **на DEV-сервере по SSH**.

## Как запускать проверки

Всё выполняется в контейнере на DEV. Рабочее дерево DEV трогать не нужно — создавайте отдельный worktree.

```bash
# на DEV
cd /home/andale/CollegePortal
git worktree add -b <branch> /tmp/work origin/develop
cp backend/.env /tmp/work/backend/.env
mkdir -p /tmp/work/backend/storage/framework/{cache,sessions,views} /tmp/work/backend/storage/logs /tmp/work/backend/bootstrap/cache
chmod -R 777 /tmp/work/backend/storage /tmp/work/backend/bootstrap/cache

V1="/tmp/work/backend:/var/www/html"
V2="/home/andale/CollegePortal/backend/vendor:/var/www/html/vendor:ro"
docker run --rm -v "$V1" -v "$V2" -w /var/www/html collegeportal-backend php artisan test
```

Образ бэкенда называется `collegeportal-backend`. Зависимости `vendor` монтируются из основного checkout — в worktree их нет.

Прогон на PostgreSQL, который ближе к бою, чем SQLite по умолчанию:

```bash
docker exec college_dev_postgres psql -U college_user -d college_portal -c "CREATE DATABASE college_portal_test"
# в .env worktree выставить DB_CONNECTION=pgsql, DB_HOST=postgres, DB_DATABASE=college_portal_test
docker run --rm --network collegeportal_default -v "$V1" -v "$V2" -w /var/www/html collegeportal-backend \
  php artisan test -c phpunit.pgsql.xml
```

Сборка фронтенда:

```bash
docker run --rm -v "/tmp/work/frontend:/app" -w /app node:22-alpine npm run build
```

Монтировать `node_modules` только на чтение нельзя: Vite пишет временные файлы. Копируйте каталог либо ставьте зависимости заново.

## Локальная рабочая копия всегда актуальна

**Владелец читает код и документацию в локальной копии, а не на серверах.** Поэтому она обязана быть на текущем стволе.

`C:\!Projects\CollegePortal` стоит на ветке `develop`, которая отслеживает `dev/develop` — remote `dev` подключён к DEV по SSH:

```
dev  ssh://andale@192.168.34.114/home/andale/CollegePortal
```

Через `origin` обновляться нельзя: он подключён по HTTPS и потребует интерактивной авторизации. Через `dev` работает по ключу, без вопросов.

Обновление локальной копии — одна команда:

```bash
git fetch dev && git merge --ff-only dev/develop
```

Настроено `pull.ff only`, поэтому случайный merge-коммит в локальной копии не появится.

**Правило сессии: закончив работу и отправив коммиты, обновите локальную копию этой командой.** Иначе владелец читает старый код, а найденные им «ошибки» окажутся уже исправленными.

Ветка `dev-line` — историческая, для работы не используется. Состояние её рабочего дерева на 08.08.2026 сохранено в `safety/dev-line-local-20260808`; проверено, что уникального кода в нём не было.

## Ветки и релизы

Ствол — `develop`. CI запускается на `develop`, `main` и ветках `feature/**`, `fix/**`, `sync/**`, `rescue/**`, `ci/**`; проверяет политику путей, тесты на SQLite и на PostgreSQL 17, сборку фронтенда и поиск секретов.

Push с рабочей станции невозможен: удалённый репозиторий подключён по HTTPS и потребует интерактивной авторизации. **Коммиты и push делаются с DEV**, где настроен доступ по SSH-ключу.

Релиз собирается только на DEV и только при чистом рабочем дереве:

```bash
bash scripts/release/build-release.sh
```

Сначала поднимите версию в `installer/VERSION`, затем соберите, затем ставьте тег — **тег на коммит сборки, а не заранее**. Обновление PROD:

```bash
# с рабочей станции, через служебную учётную запись
scp releases/college-portal-<версия>.tar.gz cp-agent@192.168.34.99:/home/cp-agent/
ssh -i .local/ssh/cp-agent cp-agent@192.168.34.99 \
  "sudo -n /opt/college-portal/installer/update.sh /home/cp-agent/college-portal-<версия>.tar.gz"
```

Скрипт сам делает резервную копию, включает режим обслуживания, мигрирует и проверяет здоровье. При неудачной проверке он **запрашивает подтверждение отката интерактивно** — в неинтерактивной сессии это не сработает, и скрипт просто завершится с ошибкой. Откат тогда делается отдельным вызовом `installer/restore.sh` с путём из строки `Backup before update:` в выводе. Если обновление запускает человек, лучше делать это в `tmux`: сессия переживёт обрыв связи и вопрос об откате дойдёт до терминала.

## Грабли, на которые уже наступали

- `frontend/public/version.json` генерируется при каждой сборке и не отслеживается в git. Не возвращайте его под контроль версий: сборка релиза требует чистого дерева и перестанет работать дважды подряд.
- `frontend/Dockerfile.release` сохраняет `version.json` из архива поверх сгенерированного. Без этого релиз представляется как `dev-unknown` в окружении `development`.
- `.env` на PROD принадлежит root. Команды, которые его читают, целиком заворачивайте в `sudo bash -c '...'`.
- Резервные копии PROD лежат в `/var/backups/college-portal`, а не в `/srv/backups`, как написано в README.
- **Право объявляется у маршрута** — `->middleware('permission:students.view')`. Таблицы префиксов в `EnsurePermission` больше нет (`ARCH-001`, шаг 3, 10.08.2026), выводить право из URL не нужно и негде. Несколько проверок на одном маршруте складываются через **И**, альтернативы внутри одной перечисляются через запятую и складываются через **ИЛИ**: `permission:digitalpasses.manage,view_own_data`. Маршрут закрытой части без объявленного права роняет `PermissionTableAndProxyTest` — либо допишите право, либо внесите маршрут в список открытых каждому вошедшему прямо в тесте.
- **Новое право обязано появиться миграцией, а не только в `RoleSeeder`.** Сидер выполняется при установке и больше никогда: `installer/update.sh` запускает миграции и ничего кроме. На этом уже потерялись `gate.points.manage` и `students.bulk_accounts` — объявлены в сидере, в базе установленной системы отсутствовали, и выдача прав их молча пропускала. Обратное тоже верно: право, заведённое только миграцией, сотрётся на новой установке, потому что `RoleSeeder` раздаёт права через `sync()`.
- **Опечатка в наборе прав роли больше не проходит молча.** `RoleSeeder::ids()` резолвит коды через `whereIn`, и код, которого нет в каталоге, просто не возвращался: установка шла зелёной, а роль недосчитывалась права — так уже терялись `gate.points.manage` и `students.bulk_accounts`. С 16.08.2026 неизвестный код роняет сидер с перечнем ненайденного; закреплено `RoleSeederCatalogueTest`. Если установка падает с «ролям раздаются права, которых нет в каталоге» — впишите право в `permissions()` **и** заведите миграцией, а не удаляйте из набора.
- **У человека не бывает двух профильных карточек одного вида.** Связи к профилю — `hasOne`, вторая карточка молча перекрывает первую, и кабинет с журналом у неё пустые: на этом стояли две карточки преподавателя у `teacher@local`. Зачисление абитуриента поодиночке теперь отказывает, если у человека уже есть карточка студента; массовое такую запись пропускает мимо (`skipped`), и это разное поведение намеренно — по одному зачисляют осознанно.
- `import.manage` разведено с `demo_data.manage` (10.08.2026): первое — загрузка данных из файлов, второе — демонстрационный набор и **очистка рабочих данных стенда**. Второе не выдано никому, кроме администратора.
- Отсутствие связанного профиля не должно давать 403. Пользователь с правом, но без профиля, обязан получать пустой список: так сделано в `DigitalIdentityController` и `TeachingLoadController`.
- Спецификация ФИС ГИА и Приёма лежит в репозитории — `docs/external-services/ФИС ГИА и Приема/`, версия 4.9. Не ищите её в `backend/storage/app/private/fis-specs/`: там пусто, а `FIS_API_OFFICIAL_SOURCES.md` про этот путь устарел.
- Официальную XSD ФИС libxml не компилирует: семь `xs:pattern` записаны в синтаксисе .NET с опережающей проверкой `(?!\s*$)`, которой в XSD 1.0 нет, и отказ идёт по всему файлу целиком. Подстановку делает `FisXsdSchema`; править сам файл нельзя, он эталон. Копия схемы для приложения лежит в `backend/resources/fis/gia-priem/4.9/` и помечена `-text` в `backend/.gitattributes` — иначе git перепишет переводы строк и копия разойдётся с оригиналом.
- Набор тестов выполняется одним процессом, и память копится за весь прогон. На 128 МБ из php.ini образа он упирался в потолок примерно на 450 тестах: сначала падал десяток не связанных между собой тестов, потом шло «Allowed memory size exhausted». Выглядит как дефект кода, а это потолок. Лимит поднят до 512 МБ в `phpunit.xml` и `phpunit.pgsql.xml`; если снова начнёт падать «непонятно что» ближе к концу прогона — сначала проверьте память.
- Пустое значение в `.env` — это пустая строка, а не «не задано»: `env('X', 'по умолчанию')` вернёт `''`. Значения по умолчанию для таких ключей задавайте через `env('X') ?: 'по умолчанию'`. На этом уже терялась настройка ФИС.
- У маршрутов `api/fis/outbound/*` на POST рядом с правом на действие может стоять ещё и `fis.outbound.create` — наследство таблицы префиксов, где POST выводился в «создание». С диагностик шлюза и обновления статуса оно снято 11.08.2026 по решению владельца: там осталось `fis.outbound.view` и `fis.outbound.status`. На формировании, отправке и отмене `create` осталось — если тестовому пользователю неожиданно приходит 403, посмотрите на объявление у маршрута, проверок там может быть две.
- Токен сессии живёт в httpOnly cookie `cp_session`, читать его из JavaScript нельзя и не нужно. Изменяющий запрос обязан нести заголовок `X-CSRF-Token` — значение лежит в читаемой cookie `cp_csrf` и выводится из самого токена. В тестах два подвоха: `withCookie` **шифрует** значение (для группы `api` нужен `withUnencryptedCookie`), а JSON-запрос вообще не отправляет cookie, пока не вызван `withCredentials()`. Без этого приложение выглядит сломанным, хотя запрос уходит без cookie.
- В ограничителе частоты `$request->user()` спрашивать бесполезно. `ThrottleRequests` есть в таблице приоритетов Laravel, `AuthenticateApiToken` — нет, и сортировщик выносит ограничитель в начало цепочки: на момент подсчёта никто ещё не разрешён. Ключ выглядит правильным и молча считает по адресу. Владельца токена берите у `App\Support\Auth\ApiTokenResolver` — он же отдаст готовый ответ middleware, лишнего запроса к базе не будет. В тестах картина другая и обманчивая: контейнер переживает запрос, `Auth::setUser` протекает вперёд, и ограничитель видит пользователя от **предыдущего** запроса — тест на `$request->user()` может пройти по неверной причине.
- ФИО, телефон и email человека пишутся только через `PersonService`: карточки студента, преподавателя и сотрудника правят Person, а свои копии получают зеркалом. Копии в `teachers` и `students` — не второй источник правды. Очистить общее поле можно только в карточке человека: в профильной пустое поле значит «не менять». СНИЛС из учебной карточки в Person не переносится — по нему человек находится и к нему привязаны документы.
- Выгрузки пишут BOM, и он стоит **перед** открывающей кавычкой первой колонки. `fgetcsv` из-за этого не считает первое поле закавыченным и отдаёт заголовок вместе с кавычками. Пока первый заголовок — одно слово («Фамилия», «Группа»), кавычек нет и всё работает; заголовок с пробелом («Код специальности») ломает разбор первой колонки, и она молча теряется. Снимать BOM надо с потока до разбора — это делает `App\Support\Csv\CsvImport`. Собственные `*CsvService` переведены на него не все: дисциплины, специальности и образовательные программы — да, остальные пять снимают BOM сами и держатся на том, что их первый заголовок без пробела.
- Поведение демонстрационного человека нельзя выводить из идентификатора строки. `DemoDataSeeder` так и делал, и `DemoDataSeederTest` краснел через раз: в полном прогоне последовательности PostgreSQL не откатываются вместе с транзакцией, набор получал идентификаторы с произвольного места (замер: 40..109 вместо 1..70), и состав опаздывающих менялся до нуля. Теперь профиль выводится из порядкового номера в наборе. То же правило годится для любых демонстрационных данных: идентификатор — это место в очереди на вставку, а не свойство человека.
- **`updateOrCreate` внутри транзакции открывает точку сохранения, и она держит блокировку до конца внешней транзакции.** С Laravel 10.31 `updateOrCreate` и `firstOrCreate` создают строку через `createOrFirst`, а тот зовёт `withSavepointIfNeeded`: если транзакция уже открыта, вставка заворачивается в `SAVEPOINT` — ради ловли гонки за уникальный ключ. Каждая точка сохранения получает собственный идентификатор транзакции, а таблица блокировок одна **на весь сервер** и вмещает `max_locks_per_transaction` × `max_connections` записей: на DEV это 64 × 100 = 6400. Демонстрационный набор набирал 4970 точек за прогон — 78 % таблицы в одиночку, и любой второй прогон рядом валился с `SQLSTATE[53200] out of shared memory`, а следом каскадом шёл `25P02`. Выглядит как мигающие тесты и «красный ствол», хотя CI зелёный: там чистый контейнер без соседей. Под `RefreshDatabase` внешняя транзакция есть всегда, поэтому в прогоне точки копятся до конца теста. Массовые записи делайте через `firstOrNew` + `fill` + `save` (в наборе это `DemoDataSeeder::writeRow`) или пакетным `upsert`; счётчик транзакций набора закрыт порогом в `DemoDataSeederTest`.
- QR-пропуск динамический и **одноразовый**: `CP2:<срок>:<подпись>` живёт 30 секунд, сервер помечает предъявленный код использованным и на повтор отвечает отказом «QR-код уже использован». Камера читает телефон в кадре несколько раз подряд, поэтому защита от дублей на экране сканирования должна быть **по значению кода, а не по времени**: любое временное окно однажды истечёт, и следующий же кадр запишет отказ. Настройка `identity.duplicate_scan_window_seconds` для динамического кода не срабатывает никогда — одноразовость проверяется раньше неё.
- Направление прохода чередуется только по **разрешённым** событиям. Отказ — не проход, человек остался по ту же сторону двери; пока отказы участвовали в расчёте, лишний скан переставлял направление, и вошедший при следующем проходе снова «входил». Так же считает присутствие `AccessPresenceService`.
- **Нарушение уникальности нельзя ловить исключением внутри транзакции.** На PostgreSQL упавший `INSERT` отравляет всю транзакцию: каждый следующий запрос в ней падает с «current transaction is aborted», и падает не там, где ошибка. На SQLite этого не происходит, поэтому такой код проходит прогон по умолчанию и краснеет только на PostgreSQL — а тесты идут в транзакции, значит и в CI. Пишите `insertOrIgnore` (это `ON CONFLICT DO NOTHING`) и смотрите на число вставленных строк; `try/catch` вокруг `create()` годится только вне транзакции. Наступили на этом в `NotificationDispatcher`.
- **`diffInSeconds` и его родня в Carbon 3 знаковые.** `$позже->diffInSeconds($раньше)` возвращает **отрицательное** число, а не модуль, как было в Carbon 2. Сравнение вида `>= порога` из-за этого молча перестаёт срабатывать: код выглядит правильным, а условие не выполняется никогда. Для «насколько одно позже другого» берите разность `getTimestamp()` — она однозначна и не зависит от версии. Наступили на этом в `ScheduleChangeNotifier`, где правка занятия отличается от создания по разнице `updated_at` и `created_at`.
- **Добавили колонку миграцией — впишите её в `$fillable` тем же коммитом.** `create()` молча отбрасывает незаполняемое, и поведение выглядит как «данные не сохранились по неизвестной причине»: на `user_identities.chat_id` это стоило прогона, три теста падали так, будто человек не начинал диалог с ботом.
- Ветка `feature/access-control-foundation` содержит вторую, невлитую реализацию контроля доступа с собственными таблицами и другим форматом токена. Не переносите оттуда патчи механически. Её проектные документы уже перенесены в `docs/ACCESS_CONTROL_*.md`, каждый помечен происхождением, а расхождения с действующей реализацией сведены в [docs/ACCESS_CONTROL_STATUS.md](docs/ACCESS_CONTROL_STATUS.md).

## Архитектурные правила

Модульная структура, миграции Laravel, Eloquent-модели и связи, Form Request Validation, Policy и Gate для доступа, сервисный слой для бизнес-логики, DTO для сложных входных данных, Resource-классы для ответов API. Изменения — небольшими шагами, после каждого этапа краткое объяснение, что изменено.
