# Digital Identity и QR-пропуска

Дата: 2026-07-01

Документ описывает QR-001: первый MVP цифровых пропусков CollegePortal на базе Identity Domain.

## Назначение

Модуль цифровых пропусков создает техническую цифровую идентичность для существующих студентов и преподавателей. Административный QR пропуска может содержать только технический `token`, а мобильный студенческий QR использует короткоживущий CP2-код.

Персональные данные в QR не записываются. ФИО, телефон, email и статус владельца доступны только через защищенный API после авторизации.

## Реализовано в QR-001

Backend:

- таблица `digital_identities`;
- модель `DigitalIdentity`;
- API выпуска, списка, отзыва и получения QR;
- SVG QR генерируется backend-сервисом;
- token создается как UUID;
- при выпуске нового активного пропуска старый активный/приостановленный пропуск этого владельца отзывается.

Frontend:

- раздел `/identity/digital-passes`;
- пункт меню `Цифровые пропуска` для администраторов и сотрудников проходной;
- личная страница `/identity/my-pass` для студентов, преподавателей и сотрудников;
- список цифровых пропусков;
- карточка выбранного пропуска справа;
- QR-код;
- выпуск пропуска для студента или преподавателя;
- отзыв пропуска;
- быстрый переход к владельцу.

Mobile Student:

- `/m/student/pass` показывает динамический CP2 QR;
- CP2 QR обновляется каждые 30 секунд;
- payload имеет формат `CP2:<expires>:<signature>`;
- в payload нет ФИО, группы, телефона, email, постоянного token или простого последовательного ID;
- подпись проверяется backend через HMAC и постоянный token пропуска;
- просроченный CP2 payload не связывается с пропуском и фиксируется как отказ `Пропуск не найден`.

## Таблица digital_identities

Поля:

- `id`;
- `entity_type`: `student` или `teacher`;
- `entity_id`;
- `token`;
- `status`: `active`, `suspended`, `revoked`, `expired`;
- `issued_at`;
- `expires_at`, nullable;
- `revoked_at`, nullable;
- `created_at`;
- `updated_at`.

## API

### GET /api/digital-identities

Возвращает список цифровых пропусков.

Фильтры:

- `entity_type`;
- `status`.
- `mine=1` — безопасный self-scope текущего пользователя.

Административный список требует `digitalpasses.manage`. Self-scope доступен через `view_own_data` или студенческий мобильный permission и всегда фильтруется на backend.

### POST /api/digital-identities/issue

Выпускает новый пропуск.

Payload:

```json
{
  "entity_type": "student",
  "entity_id": 1,
  "expires_at": null
}
```

### POST /api/digital-identities/{id}/revoke

Отзывает пропуск.

### GET /api/digital-identities/{id}/qr

Возвращает SVG QR-код. QR содержит только token.

Пользователь без `digitalpasses.manage` может получить QR только своего пропуска. Чужой QR запрещается контроллером.

### GET /api/mobile/student

Возвращает данные мобильного кабинета студента и динамический QR:

- `qr_svg`;
- `qr_expires_at`;
- `qr_refresh_seconds = 30`.

Frontend обновляет QR до истечения срока действия.

### POST /api/access/scan

Проверяет QR-token на backend и фиксирует событие проходной.

### GET /api/access/events

Возвращает журнал событий проходной.

## Безопасность

- QR не содержит ФИО, телефон, email, группу, должность или другие персональные данные.
- Административный QR содержит только случайный token/UUID.
- Мобильный студенческий QR содержит только короткоживущий CP2 payload с HMAC-подписью.
- SVG QR отдается только через защищенный API.
- Проходная проверяет token на backend и только затем показывает оператору разрешенные данные.
- Отозванный или просроченный token не должен давать доступ.
- Raw token не отдается в JSON пользователю без `digitalpasses.manage`.

## Связь с Identity Domain

QR-001 пока использует `entity_type` и `entity_id`, чтобы не ломать существующие таблицы. В будущем эта таблица должна быть связана с `Person` и `Digital Identity` из `docs/IDENTITY_DOMAIN.md`.

Текущая модель является переходной:

- сейчас: `student` / `teacher`;
- сейчас также поддерживается `person_id` как переходная связь с Person;
- дальше: QR, Mobile QR, RFID/NFC, Face ID без изменения пользовательских сценариев.
