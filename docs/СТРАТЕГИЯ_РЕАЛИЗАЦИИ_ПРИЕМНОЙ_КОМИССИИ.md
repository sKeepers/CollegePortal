# Общая архитектура реализации

Подсистема реализуется эволюционно: сначала совместимый backend foundation, затем постепенный перевод UI и расширение бизнес-процессов. Существующий `/admissions` не ломается и остается рабочим в течение переходного периода.

Целевая архитектура:

```text
Frontend Admissions Workspace
  -> Admissions API
    -> Application Services
      -> Domain Services
        -> Repositories
          -> Database / Private Storage / Audit / Reference Data
```

Основные правила реализации:

- backend является источником истины для RBAC, статусов и бизнес-ограничений;
- frontend строится вокруг API capabilities и не зашивает доступные действия;
- миграции выполняются поэтапно с dry-run/backfill;
- документы хранятся только в private storage;
- ФИС остается отдельным integration layer;
- критичные действия имеют подтверждение, Audit и идемпотентность;
- большие изменения делятся на маленькие PR.

# Backend

Backend реализуется слоями:

1. migrations и Reference Data;
2. модели и связи;
3. repositories;
4. services/actions;
5. policies/permissions;
6. controllers/resources/requests;
7. tests.

Первый backend slice должен быть минимальным:

- справочники и статусы;
- read-only список заявлений;
- карточка заявления;
- создание Applicant/Application;
- базовый Audit;
- RBAC 403/200;
- совместимость текущего `/admissions`.

# Frontend

Frontend реализуется после появления стабильного backend slice.

Принципы:

- использовать существующий Quasar/UI Foundation;
- не создавать новый frontend-проект;
- строить экран как рабочее место приемной комиссии: таблица, фильтры, WorkspacePanel, вкладки;
- получать доступные действия из API;
- скрывать кнопки по permissions, но не считать это защитой;
- для критичных действий показывать preview/confirmation.

Первый frontend slice:

- список заявлений на новом API;
- карточка заявления read-only;
- фильтры и KPI;
- отображение комплектности документов;
- graceful fallback, если новый endpoint недоступен.

# Domain

Domain слой содержит бизнес-понятия и правила:

- Applicant;
- Application;
- ApplicationChoice;
- ApplicationDocument;
- DocumentFile;
- Achievement;
- Exam;
- Competition;
- CompetitionApplication;
- AdmissionOrder;
- AdmissionOrderItem;
- Enrollment;
- ApplicationEvent.

Domain не должен знать о HTTP, Vue, Quasar или GitHub. Он работает с объектами, статусами, правами, событиями и исключениями.

Основные domain rules:

- Person не объединяется автоматически только по ФИО;
- `documents_provided` не равен полной комплектности;
- `ready_for_enrollment` не выставляется автоматически из-за документов;
- Recommendation не равна приказу;
- Order approval не равен Enrollment apply;
- Enrollment apply идемпотентен;
- утвержденный приказ нельзя редактировать обычным CRUD.

# Application

Application слой оркестрирует use cases:

- CreateApplicant;
- ResolveApplicantDuplicate;
- CreateApplication;
- RegisterApplication;
- UpdateApplication;
- ReceiveDocument;
- VerifyDocument;
- RecalculateCompleteness;
- AddApplicationToCompetition;
- RecalculateCompetitionRanking;
- RecommendApplication;
- CreateAdmissionOrder;
- ApproveAdmissionOrder;
- PreviewEnrollment;
- ApplyEnrollment;
- PreviewFisPackage;

Каждый use case:

- проверяет permission;
- валидирует состояние;
- вызывает domain service;
- пишет Audit;
- возвращает DTO/result object;
- не возвращает raw private data.

# Infrastructure

Infrastructure слой отвечает за внешние зависимости:

- PostgreSQL;
- private storage;
- Audit Log;
- Reference Data;
- Queue jobs, если появятся тяжелые операции;
- FIS integration layer;
- file antivirus/checksum hooks, если будут добавлены позже.

Infrastructure не должен определять бизнес-правила. Он предоставляет adapter/repository implementation для application/domain слоев.

# Repository

Repository слой нужен для сложных выборок, фильтров и сохранения агрегатов.

Минимальные repositories:

- ApplicantRepository;
- ApplicationRepository;
- ApplicationDocumentRepository;
- CompetitionRepository;
- OrderRepository;
- EnrollmentRepository;
- AdmissionsReferenceRepository;
- AdmissionsEventRepository.

Правила:

- фильтры API не копируются вручную в controllers;
- pagination и сортировка централизуются;
- bulk/filter selection не должен зависеть от pagination;
- write operations выполняются транзакционно;
- уникальность проверяется и на уровне БД, и на уровне service.

# Services

## ApplicantService

Отвечает за создание Applicant, поиск дублей, связь с Person и архивирование профиля.

## ApplicationService

Отвечает за создание, регистрацию, редактирование и отзыв заявления.

## DocumentService

Отвечает за registry документов, private files, проверку, отклонение и замену.

## CompletenessService

Считает `documents_count`, `required_documents_count`, `documents_status`, missing list. Не меняет `ready_for_enrollment` без отдельной команды.

## CompetitionService

Отвечает за конкурсные строки, рейтинг, рекомендации и предупреждения.

## OrderService

Отвечает за проекты приказов, строки, утверждение, отмену и блокировки.

## EnrollmentService

Отвечает за preview/apply, защиту от дублей студентов и идемпотентность.

## AdmissionsFisPackageService

Формирует внутренний snapshot для ФИС без production-отправки.

# Audit

Audit обязателен для всех write operations:

- создание и изменение Applicant;
- создание, регистрация, отзыв и изменение Application;
- работа с choices;
- прием, загрузка, проверка и отклонение документов;
- достижения и экзамены;
- конкурс и рейтинг;
- приказ;
- preview/apply зачисления;
- ФИС preview/package/validation/download;
- изменение справочников.

Audit payload:

- хранит `request_id`, actor, entity, event code, masked before/after, reason;
- не хранит полный паспорт, СНИЛС, raw ФИС payload, файлы, токены и секреты;
- для скачивания файлов фиксирует факт доступа, но не содержимое.

# RBAC

Permissions берутся из [RBAC приемной комиссии](RBAC_ПРИЕМНОЙ_КОМИССИИ.md).

Реализация:

- middleware/policy проверяют доступ на backend;
- frontend использует permissions только для UX;
- read-only роли не получают write endpoints;
- applicant portal ограничивается собственными данными;
- критичные permissions требуют confirmation и reason.

Минимальный первый набор:

- `admissions.applicant.view`;
- `admissions.applicant.manage`;
- `admissions.application.view`;
- `admissions.application.create`;
- `admissions.application.update`;
- `admissions.application.register`;
- `admissions.application.manage`;
- `admissions.documents.view`;
- `admissions.documents.receive`;
- `admissions.events.view`;
- `admissions.reference.view`.

Plural permissions `admissions.applicants.*` и `admissions.applications.*` зарезервированы для будущего полного CRUD и не используются foundation API BACK-002/BACK-003.

# Работа с файлами

Файлы документов:

- хранятся в private storage;
- скачиваются только через backend controller;
- имеют checksum SHA-256;
- имеют MIME/type validation;
- не пишутся в Audit;
- не попадают в Git, logs или public storage;
- могут быть заменены, но история замены сохраняется.

Первый implementation slice может поддержать только безопасный registry и metadata, а загрузку файлов вынести во второй slice, если это снизит риск.

# Стратегия миграций

Миграции выполняются только после отдельной задачи ADM-004/BACK-001.

Последовательность:

1. Reference Data и permissions.
2. Applicant/Application transition fields.
3. Choices.
4. Documents registry.
5. Document files.
6. Achievements и Exams.
7. Competitions.
8. Orders.
9. Enrollments.
10. Events/Audit improvements.

Обязательные условия:

- dry-run текущих данных;
- nullable transition fields там, где есть исторические пробелы;
- backfill без удаления существующих полей;
- индексы и uniqueness включаются после проверки дублей;
- rollback plan для каждого шага;
- production-like данные не использовать в тестах.

# Стратегия тестирования

Уровни тестов:

- unit tests для domain services;
- feature tests для API endpoints;
- policy/RBAC tests;
- migration/backfill tests;
- audit tests;
- file storage tests;
- frontend component tests;
- end-to-end smoke для основных сценариев.

Минимальные сценарии:

- создать Applicant без дубля;
- остановить создание при неоднозначном дубле;
- создать Application;
- зарегистрировать Application;
- принять документ;
- комплектность no/incomplete/complete;
- оператор не утверждает приказ;
- директор не пишет данные;
- зачисление preview не меняет БД;
- повторный apply не создает дубль Student;
- Audit не содержит чувствительные данные.

## BACK-003.1: изоляция legacy и foundation

- общая таблица `applicant_applications` получает технический классификатор `record_type`;
- старые записи и старый API `/api/applicant-applications` используют только `record_type=legacy`;
- новый API `/api/admissions/applications` использует только `record_type=foundation`;
- foundation-запись дополнительно требует `applicant_id` и `foundation_version`;
- legacy route-model binding отсекает foundation-записи как `404`;
- CSV/import/export/bulk/dashboard/FIS package preparation остаются в legacy-контуре до отдельной миграции процессов;
- это временная совместимость переходного периода, а не целевая финальная модель.
