# Задача SEC-006: ограничитель частоты считает по адресу, а не по человеку

Скопируйте текст ниже целиком в новый чат.

---

Прочитай `CLAUDE.md`, `docs/ACTIVE_WORK.md` (раздел «Обход прав по всем ролям») и пункт `SEC-006` в `TASKS.md`. Работай по правилам из `CLAUDE.md`.

## Что нужно сделать

Ограничитель `api.authenticated` считает запросы **по IP-адресу, а не по учётной записи**. Снаружи весь колледж приходит через один NAT, поэтому общие 120 запросов в минуту выбираются несколькими одновременно работающими людьми, и портал начинает отдавать `429` всем сразу.

## Причина уже установлена, не ищи заново

В `AppServiceProvider` ключ задан как `$request->user()?->id ?: $request->ip()`. Выглядит правильно, но `ThrottleRequests` в Laravel по приоритету идёт **раньше** `api.token`: в момент подсчёта пользователь ещё не разрешён, `user()` пуст, и ключом всегда оказывается адрес.

**Проверено на стенде:** `study@local` получает `x-ratelimit-remaining: 119`, следующий за ним `director@local` — `118`. Счётчик один на всех.

Чинить либо порядком middleware, либо разбором токена внутри самого ограничителя.

## Почему это первым

Сегодня не жмёт: на PROD контингента нет, на DEV работает один человек. Но портал готовят к работе, и в первый же день, когда из колледжа зайдут несколько сотрудников, они начнут выбивать друг друга. Дефект известен, диагноз точен, объём небольшой — дешевле закрыть заранее, чем разбираться под звонки.

## На что обратить внимание

- **Ограничитель входа — отдельный.** `throttle:auth.login` уже чинили по находке 1 аудита: там ключ считается по учётной записи, в которую стучатся. Не сломай это и не смешивай два ограничителя.
- Проверь остальные `RateLimiter::for(...)` в `AppServiceProvider`: если ключ строится так же, дефект тот же.
- Разбор токена внутри ограничителя не должен превращаться во второй механизм авторизации: он определяет ключ счётчика, а не даёт доступ. Невалидный токен — считать по адресу.
- Значение лимита не подбирай на глаз: если предлагаешь менять число, объясни, из чего оно взято.

## Проверки

Тесты на DEV в отдельном worktree, ветка от `origin/develop`, прогон на SQLite и на PostgreSQL 17.

Тест должен воспроизводить именно суть: **два разных пользователя с одного адреса имеют независимые счётчики**, а один пользователь с двух адресов — общий. Без этого правка выглядит сделанной, но не проверенной.

Заголовки `x-ratelimit-remaining` удобно смотреть и вручную на живом DEV — так дефект и нашли.
