# Задача ARCH-001: права не должны выводиться из префикса URL

Скопируйте текст ниже целиком в новый чат.

---

Прочитай `CLAUDE.md`, `docs/ACTIVE_WORK.md` и `docs/ACCESS_CONTROL_STATUS.md`. Работай по правилам из `CLAUDE.md`.

## Что нужно сделать

Убрать источник повторяющихся дефектов: в `backend/app/Http/Middleware/EnsurePermission.php` требуемое право **угадывается по префиксу URL** по таблице внутри middleware, и при отсутствии совпадения молча возвращается `reference.manage`.

Последствия ровно два, оба тихие:

- новый маршрут, забытый в таблице, даёт законному пользователю необъяснимое «нет прав»;
- либо, наоборот, маршрут получает право, которое к нему не относится, и доступ оказывается шире задуманного.

Ошибка не проявляется ни при обзоре кода, ни в тестах маршрута — она появляется у пользователя с конкретной ролью.

## Как это чинить

Право должно объявляться **у маршрута**, а не выводиться из строки пути. Целевое состояние: `Route::...->middleware('permission:students.view')` для каждого маршрута, а таблица префиксов исчезает.

Это затрагивает почти весь `backend/routes/api.php`, поэтому **сначала покажи план и дождись подтверждения**. В плане ответь:

1. Как переходить постепенно, чтобы не сломать доступ в середине пути.
2. Что делать со случаями, где право зависит от метода: сейчас `GET` даёт `view`, а `POST` — `create`, и это зашито в `methodPermission()`.
3. Что делать с исключениями, которые уже есть: `api/digital-identities` и `api/teaching-loads` на `GET` допускают `view_own_data`; человек с правом, но без связанного профиля, обязан получать **пустой список, а не 403** — так сделано в `DigitalIdentityController` и `TeachingLoadController`, это поведение сохранить.
4. Как гарантировать, что маршрут без объявленного права не попадёт в систему: тест, который перебирает все маршруты и падает, если у маршрута нет явного права, — надёжнее любой договорённости.

## Что проверить попутно

Пока разбираешься с правами, сверь их с интерфейсом: бывает, роль видит пункт меню, но получает 403, или наоборот — право есть, а пункта нет. Отдельно проверь роли `study` и `study_records`: «Учебную часть» разделили на две недавно, устаревший дубль `academic_office` намеренно не тронут.

Найденные расхождения не чини молча — перечисли их и предложи, как должно быть.

## Проверки

Тесты на DEV в отдельном worktree, ветка от `origin/develop`, прогон на SQLite и на PostgreSQL 17.

Главная проверка — не «тесты зелёные», а покрытие ролями: для каждой роли из `RoleSeeder` пройди её маршруты и убедись, что доступ соответствует задуманному. Права роли `security`, `hr`, `study`, `study_records`, `teacher` и `student` проверь отдельно: у них самый узкий набор, и именно на них молчаливый откат к `reference.manage` даёт ложное «нет прав».

## Когда закончишь

Коммить и пушить с DEV, обновить `docs/ACTIVE_WORK.md` и `TASKS.md` (закрыть `ARCH-001`), затем **обновить локальную рабочую копию**:

```bash
git fetch dev && git merge --ff-only dev/develop
```

На PROD не разворачивать без отдельного поручения: ошибка в правах закрывает людям работу.
