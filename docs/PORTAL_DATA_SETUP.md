# Начальное заполнение базы CollegePortal

## Назначение

Документ задает безопасный порядок первичного заполнения рабочей базы CollegePortal в соответствии с текущей реализацией. Выполняйте шаги в указанной последовательности: последующие сущности ссылаются на ранее созданные записи.

Инструкция не заменяет локальные приказы, правила обработки персональных данных и порядок выдачи учетных данных колледжа. Не вносите в документацию, примеры, тесты или общие файлы реальные пароли, паспортные данные, СНИЛС, телефоны, адреса и иные персональные данные.

## Перед началом

1. Определите ответственное лицо за каждый набор данных и согласуйте дату актуальности выгрузки.
2. Подготовьте небольшой пилотный набор и резервную копию базы согласно принятому регламенту.
3. Проверьте справочники и данные в исходных файлах по [REAL_DATA_CHECKLIST](REAL_DATA_CHECKLIST.md).
4. Для массовой загрузки используйте `/admin/import` и описания в [import-templates](import-templates/README.md). Сначала загружайте пилотный набор, проверяйте результат, затем полный объем.
5. Создавайте учетные записи только для лиц, которым необходим вход. Наличие Person, Employee, Teacher или Student само по себе не создает User.

## Правила идентификации и автогенерации

- `Person` является общей карточкой физического лица. Не создавайте несколько Person для одного человека без обоснования.
- При создании Employee система сначала использует выбранный `person_id` либо ищет возможный Person по СНИЛС, email, телефону, ФИО и дате рождения. При нескольких совпадениях запись нужно выбрать и проверить вручную.
- Для преподавателя кадровая цепочка должна быть `Person -> Employee -> Teacher`: при создании или обновлении Employee с `is_teacher=true` система создает либо синхронизирует Teacher с тем же `person_id`.
- Не заполняйте табельный номер вручную без утвержденной потребности: если `employee_number` не передан, `HrService` автоматически создает его в формате `EMP-000001` по следующему идентификатору Employee.
- Не задавайте вручную код подразделения или должности, если нет утвержденного внешнего кода. При пустом `code` текущие контроллеры генерируют уникальный код из названия подразделения или должности.
- Для специальностей, дисциплин и учебных планов код также может формироваться автоматически. Официальный код специальности или дисциплины, если он есть в утвержденных данных, следует сохранить явно.
- Имя группы уникально. До загрузки унифицируйте написание групп, дисциплин, аудиторий и значений справочников.

## 1. Системный доступ и роли

Системный администратор первым создает необходимые учетные записи в разделе `/admin/users`, назначает основную роль и при необходимости дополнительные роли. Учетная запись содержит отображаемое имя, уникальный рабочий email, пароль, статус активности, основную роль и, при наличии, связь с Person.

Пароль задает уполномоченный администратор через защищенный канал. Документ не устанавливает его значение и не содержит примеров паролей. После выдачи доступа следует проверить вход и при необходимости смену пароля по локальному регламенту.

| Назначение из Users.txt | Текущая системная роль | Профиль Person / примечание |
| --- | --- | --- |
| Системный администратор | `admin` | Может быть без профильной карточки; не использовать эту роль как обычную рабочую. |
| Директор | `director` | Для сотрудника рекомендуется Person и Employee. |
| Отдел кадров | `hr` | Person и Employee для работника кадровой службы. |
| Учебная часть (студенты) | `study` | Отдельная учетная запись с функциональным назначением в имени. |
| Учебная часть (расписание/нагрузка) | `study` | Отдельная учетная запись с функциональным назначением в имени. |
| Приемная комиссия | `admission` | Person и Employee для работника приемной комиссии при ведении кадрового контура. |
| Преподаватель | `teacher` | Связать с Person; для штатного или привлеченного преподавателя создать Employee с `is_teacher=true`, который создаст Teacher. |
| Сотрудник, который является куратором | `curator` как дополнительная роль при необходимости | Сначала Person и Employee; назначение куратором группы требует Teacher, поэтому сотрудника-куратора нужно создать с `is_teacher=true`. |
| Студент | `student` | Связать с Person и профилем Student. |
| Охрана | `security` | Person и Employee для сотрудника проходной при ведении кадрового контура. |

Текущие ограничения:

- В RoleSeeder есть одна роль `study`; отдельных кодов ролей для ведения студентов и для расписания/нагрузки нет. Разделяйте эти обязанности двумя User и организационным регламентом, а не выдуманными кодами ролей.
- В системе нет отдельной системной роли `employee`. `Employee` - кадровый профиль, а не роль доступа. Для сотрудника без специального рабочего контура создавайте User только после согласования минимально необходимой существующей роли.
- `curator` является дополнительной ролью доступа. Связь куратора с группой хранится в `groups.curator_id` и ссылается на Teacher, а не непосредственно на Employee.
- User допускает `person_type=employee`, но `person_id` в текущем API должен быть идентификатором Person. Не подставляйте в него идентификатор Employee, Teacher или Student.

После создания User проверьте основную роль в `users.role_id` и набор ролей в `role_user`; при нескольких ролях одна из них должна быть основной. Блокировка User отключает вход, но не удаляет Person и профиль сотрудника или студента.

## 2. Подразделения и должности

Ответственный: отдел кадров совместно с системным администратором.

1. В `/hr/departments` создайте дерево подразделений: например, администрацию, отдел кадров, учебную часть, приемную комиссию и отделения. Для вложенного подразделения укажите родительское.
2. Для каждого подразделения заполните название, тип, активность и руководителя только после создания соответствующего Employee.
3. Оставьте `code` пустым, если официальный код не утвержден: он будет сгенерирован автоматически. Укажите внешний код только при необходимости интеграции или сверки с утвержденным справочником.
4. В `/hr/positions` создайте используемые должности: директор, методист, диспетчер, специалист отдела кадров, преподаватель, сотрудник охраны и другие фактически применяемые. Для преподавательских должностей установите признак преподавательской должности.
5. Проверьте, что неактивные подразделения и должности не выбираются для новых назначений.

Не удаляйте подразделение или должность, если они уже используются. Сначала переназначьте связанные записи либо деактивируйте запись согласно доступному сценарию.

## 3. Person, Employee и Teacher

Ответственный: отдел кадров. Создавайте Person через карточку сотрудника или выбирайте уже существующую личную карточку после проверки совпадений.

Для каждого сотрудника подготовьте:

- ФИО; при наличии - дату рождения;
- рабочие контакты только при законном основании и необходимости;
- кадровый статус, тип занятости, дату приема, ставку;
- основное подразделение и должность;
- номер и дату кадрового документа, если они ведутся в системе;
- признак `is_teacher` для преподавателя или сотрудника, который должен быть куратором.

### Массовая загрузка сотрудников

В `/admin/import` выберите «Сотрудники» и скачайте «Шаблон Excel». XLSX-шаблон содержит русские колонки: табельный номер, ФИО, Email, телефон, подразделение, должность, дату приема, статус, занятость, ставку, признак преподавателя, рабочий график и признак создания учетной записи. Строка-пример не содержит персональных данных и перед загрузкой должна быть удалена или заменена.

Табельный номер можно оставить пустым: при создании сотрудника система сформирует его автоматически. Подразделение и должность должны совпадать ровно с названием или уникальным кодом уже созданного справочника; неоднозначные совпадения блокируют проверку. Указывайте дату приема как `ДД.ММ.ГГГГ`, преподавателя как «Да» или «Нет», а статус и занятость - русскими значениями из шаблона. Загрузите XLSX или CSV, проверьте предпросмотр и сопоставление колонок, выполните проверку и только затем подтвердите импорт.

Рабочий график указывается подписью из карточки сотрудника: «Пн–Пт, 09:00–18:00», «Пн–Пт, 09:00–17:00», «Сменный 2/2, 08:00–20:00» или «Гибкий график». Тире и пробелы распознаются в любом виде, пустая ячейка оставляет график незаданным, а незнакомое значение останавливает строку с указанием колонки. Колонка «Создать учетную запись» со значением «Да» заводит пользователя с ролью «Сотрудник», связанного с тем же Person; логином становится телефон, при его отсутствии - email. Пароль генерируется случайным и в результат импорта не попадает, поэтому перед выдачей доступа его нужно сменить в разделе пользователей. Если у Person уже есть учетная запись, строка вернет ошибку - сотрудник при этом будет создан, а учетную запись нужно связать вручную.

Порядок приема:

1. В `/hr/employees` создайте Employee, выбрав существующий Person либо указав ФИО и разрешенные контакты для новой личной карточки.
2. Укажите дату приема, статус, тип занятости, основное подразделение, должность и ставку. Табельный номер оставьте пустым для автогенерации.
3. Для преподавателя или будущего куратора включите `is_teacher=true`. Система синхронизирует профиль Teacher с Person, должностью и подразделением.
4. Во вкладке назначений добавьте основное назначение с подразделением, должностью, ставкой, датой начала и при необходимости реквизитами приказа. Основное назначение синхронизирует основные поля Employee.
5. Для отпусков, больничных, командировок и иных кадровых периодов добавляйте отдельные status periods. Они дают расписанию предупреждение о недоступности преподавателя, но не отменяют занятие автоматически.
6. После создания кадрового профиля создайте или свяжите User с Person и назначьте роль из раздела 1.

Если преподаватель уже был внесен старым модулем Teachers, сначала проверьте его Person и Employee. Не создавайте дубликат: `Teacher` и `Employee` связываются общим `person_id`.

## 4. Справочники, специальности и образовательные программы

Ответственный: учебная часть; системный администратор обеспечивает доступ.

1. В `/admin/reference` проверьте стартовые системные справочники: формы обучения и финансирования, виды занятий и нагрузки, статусы студентов, виды контроля, экзаменов и документов.
2. Создайте дополнительные пользовательские справочники только там, где они действительно требуются процессом. Код справочника и элемента - стабильный технический идентификатор; в пользовательском интерфейсе показывается русское название.
3. Значения, которые уже могли попасть в данные, не удаляйте: деактивируйте их.
4. Создайте специальности с официальным кодом, названием, квалификацией, нормативным сроком обучения и уровнем образования.
5. Для каждой комбинации специальности, набора, формы обучения и срока создайте образовательную программу. Год начала и форма обучения входят в уникальность программы.
6. Создайте справочник дисциплин до учебных планов, нагрузки и расписания. Для преподавателей укажите доступные дисциплины, если это требуется для контроля назначения.
7. Создайте аудитории с номером, корпусом, вместимостью и доступными признаками до составления расписания.

## 5. Учебные планы и группы

Ответственный: учебная часть.

1. Создайте учебный план для образовательной программы и года набора: название, код при наличии, квалификацию, год, семестры и статус.
2. Добавьте `curriculum_subjects`: дисциплину, семестр, часы по видам, общий объем, тип контроля, последовательность, признак факультативности и компетенции при наличии утвержденных данных.
3. Допустим импорт по шаблону [curricula](import-templates/curricula.md). До импорта должны существовать образовательные программы и дисциплины.
4. Для каждой фактической группы создайте уникальное название, специальность, образовательную программу, курс и год набора.
5. Привяжите группе действующий `curriculum_id`. Без этой связи генератор нагрузки не сможет получить дисциплины плана.
6. Назначьте куратора только после создания Teacher. Если куратор является сотрудником, он также должен иметь профиль Teacher через `is_teacher=true`.

`curriculum_items` сохраняется для совместимости, но новое заполнение должно опираться на `curriculum_subjects` и связь группы с учебным планом.

## 6. Студенты и их доступ

Ответственный: учебная часть (студенты).

1. Убедитесь, что группа, образовательная программа и учебный план созданы.
2. Создайте Student в нужной группе, указав ФИО, статус, дату зачисления и действующий СНИЛС. API и массовые импорты проверяют контрольное число СНИЛС, нормализуют его и используют хеш для безопасного поиска Person.
3. Система связывает Student с Person по нормализованному хешу СНИЛС и повторно использует найденную карточку. Не объединяйте людей только по ФИО.
4. Для студента, которому нужен личный кабинет, создайте User с ролью `student` и свяжите его с тем же Person. Учетную запись создавайте после карточки студента.
5. Проверьте группу, статус и учетную запись на небольшой выборке. Не загружайте следующий массив, пока не устранены дубли и ошибки связей.

Для массовой загрузки используйте [students](import-templates/students.md) после загрузки групп. Для новых студентов CSV и Universal Import требуют колонку СНИЛС с действующим контрольным числом; при обновлении уже найденного студента СНИЛС можно не передавать. При приемной кампании foundation-профиль также требует СНИЛС: для нового Person он проверяется, а выбранный `person_id` должен ссылаться на карточку с заполненным СНИЛС.

## 7. Нагрузка и расписание

Ответственный: учебная часть (расписание/нагрузка).

Предусловия: у группы есть `curriculum_id`; в плане есть `curriculum_subjects`; преподаватели, дисциплины, аудитории и виды занятий созданы.

1. Для каждой группы и учебного года вызовите генерацию нагрузки сначала через `POST /api/teaching-load/generate/preview` или соответствующий экран. Проверьте дисциплины, семестры, плановые часы, конфликты ручных строк и строки без преподавателя.
2. Только после проверки выполните `POST /api/teaching-load/generate/apply`. Повторное применение обновляет сгенерированные строки и не должно создавать дубли; ручные строки генератор не перезаписывает.
3. Назначьте преподавателя строкам нагрузки вручную. Автоматический подбор преподавателя в MVP отсутствует.
4. Проверьте coverage: плановые, назначенные, неназначенные и сверхназначенные часы.
5. Для каждой записи расписания сначала используйте `preview`, затем устраните blocking-конфликты и только потом выполняйте `apply`.
6. Расписание должно ссылаться на допустимую строку нагрузки: сочетание группы, дисциплины и преподавателя проверяется системой. Контролируются пересечения преподавателя, группы и аудитории, а также превышение часов.
7. Кадровая недоступность преподавателя выводится как warning. Она требует решения диспетчера или замены, но не отменяет занятие автоматически.

Для пилотного импорта соблюдайте порядок шаблонов [teaching-load](import-templates/teaching-load.md), затем [schedule](import-templates/schedule.md). После импорта обязательно проверьте конфликты и покрытие, так как прямой CSV-импорт является совместимым контуром, а Schedule Engine - контролируемым путем изменений.

## 8. Электронный журнал

Ответственные: преподаватель, учебная часть для контроля.

1. Открывайте журнал из конкретного `schedule_entry`; при первом открытии создается один `journal_lesson` и строки посещаемости для активных студентов группы.
2. Преподаватель заполняет тему, домашнее задание, посещаемость и оценки. Статусы посещаемости: `present`, `absent`, `late`, `excused`, `sick`, `remote`.
3. Подсказка проходной по посещаемости является только предложением: она не изменяет журнал, пока преподаватель явно не применит ее.
4. После проверки преподаватель завершает и подписывает занятие. Подписанный журнал нельзя штатно редактировать; исправление требует права `journal.reopen` и фиксируется в аудите.
5. Учебная часть проверяет незаполненные, завершенные и подписанные занятия через контрольный режим `journal.view_all`.

## Контроль завершения начального заполнения

- Созданы только необходимые User, у каждого есть активность, основная роль и, где применимо, связь с Person.
- Созданы подразделения, должности, сотрудники и назначения; табельные номера и коды проверены как сгенерированные или официально заданные.
- Для преподавателей и кураторов подтверждена цепочка Person, Employee и Teacher; у групп назначены корректные Teacher-кураторы.
- Справочники, специальности, программы, дисциплины и аудитории согласованы между собой.
- Каждая группа связана с образовательной программой и актуальным учебным планом; студенты находятся в корректных группах.
- По нагрузке устранены критические неназначенные строки, по расписанию отсутствуют blocking-конфликты.
- На пилотных занятиях открывается журнал, создаются строки посещаемости и соблюдается разграничение доступа.
- Результаты пилотной загрузки, ошибки и принятые решения зафиксированы без персональных данных и паролей.

## Актуализация документации

Этот документ и ссылки на него в `docs/README.md` должны обновляться в той же задаче, в которой изменяется алгоритм начального заполнения, автогенерация табельного номера или кодов, модель связей Person/Employee/Teacher, роли и права, импорт, учебные планы, нагрузка, расписание или журнал. Изменение кода без актуализации этой инструкции считается незавершенным для соответствующего процесса.
