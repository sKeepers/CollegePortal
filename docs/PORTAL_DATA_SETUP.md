# Подготовка CollegePortal к переносу на другой компьютер

## Назначение

Регламент описывает безопасный перенос CollegePortal на новый компьютер или сервер.
Он не заменяет `INSTALLATION.md`, `BACKUP_RESTORE.md` и `DEPLOYMENT.md`, а задает порядок
их применения без удаления или автоматического восстановления данных.

## Границы безопасности

- Новый экземпляр сначала устанавливается отдельно от действующих DEV и PROD.
- В Git не переносятся `.env`, `.secrets`, сертификаты, ключи, архивы backup, дампы БД,
  реальные XLS/XLSX/CSV-выгрузки и персональные данные.
- Исходный компьютер и его данные не изменяются в ходе подготовки.
- Восстановление БД или private storage выполняется только после отдельного подтверждения
  ответственного лица и точной фразы, требуемой `installer/restore.sh`.
- ФИС не получает `apply` или TEST/production-отправку в рамках переноса.

## Что передается

1. Проверенный release-архив CollegePortal и его SHA-256 checksum.
2. Отдельно и защищенным каналом: backup, включающий PostgreSQL dump, private storage,
   защищенную копию `.env` и manifest с checksum.
3. Параметры нового окружения: DNS/IP, HTTPS-режим, часовой пояс, исходящие почтовые и
   интеграционные настройки. Секреты передаются только через утвержденное хранилище секретов.
4. При использовании ФИС Gateway: отдельный Windows-пакет Gateway и его private config;
   правила firewall сохраняют доступ только с утвержденного узла DEV.

## Порядок переноса

1. На новом Ubuntu Server подготовить Docker и выполнить чистую установку release-архива по
   `INSTALLATION.md`. Установка размещается в `/opt/college-portal` и не должна выполняться
   поверх `/srv/college-dev` или действующего PROD.
2. Не создавая и не восстанавливая реальные данные, запустить проверку:

```bash
sudo /opt/college-portal/installer/check.sh
```

3. Проверить `/health/ready`, вход первого администратора и frontend в выбранном HTTPS-режиме.
4. Сверить версию приложения, manifest backup и SHA-256 всех передаваемых файлов.
5. Получить отдельное письменное подтверждение перед запуском restore. Команда восстановления
   намеренно не приводится как действие по умолчанию: она описана в `BACKUP_RESTORE.md` и
   требует точной фразы подтверждения.
6. После подтвержденного восстановления повторить `installer/check.sh`, проверить доступ,
   роли, private storage и только затем выполнить согласованные UAT-сценарии.

## ФИС и интеграции

- Inbound ФИС-импорт требует dry-run и не должен быть применен при переносе.
- Outbound ФИС остается выключенным, пока не установлены официальные спецификации, TEST
  credentials и защищенный доступ согласно `FIS_OPERATIONS_GUIDE.md`.
- Gateway на Windows устанавливается по `INTEGRATION_GATEWAY_WINDOWS_INSTALLATION.md`; ViPNet
  и firewall не отключаются для диагностики.

## Приемка переноса

- `installer/check.sh` завершается успешно.
- Backup manifest и SHA-256 совпадают.
- Не появились secrets, сертификаты, dumps или реальные импорты в Git worktree.
- DEV и PROD не были изменены без отдельного согласования.
- В `docs/ACTIVE_WORK.md` зафиксированы новый путь, версия, результаты проверок и решение по
  фактическому восстановлению данных.
