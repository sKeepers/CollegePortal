# EPIC-001: Architecture Review после Release 0.7

Дата: 08.07.2026.  
Окружение анализа: DEV `/srv/college-dev`.  
PROD: не анализировался и не изменялся.

## Цель

Оценить архитектуру CollegePortal после Release 0.7 без изменения бизнес-логики, БД и API. Документ фиксирует текущее состояние, сильные стороны, риски и направления технического улучшения.

## Общая оценка

CollegePortal вырос из MVP в платформу с несколькими связанными доменами: учебный контур, приемная комиссия, Identity/Access, выпуск/дипломы, FRDO/FIS, администрирование, импорт, аудит, настройки и справочники. Архитектура уже разделена на Laravel backend и Vue/Quasar frontend, есть сервисный слой, Form Request, Resource-классы, Pinia stores и документация.

Главный архитектурный вызов после Release 0.7: быстрый рост функциональности привел к крупным сервисам и страницам. Это нормально для MVP, но перед масштабированием на реальные данные нужно постепенно выделять доменные сервисы и переиспользуемые frontend-композиции.

## Backend

### Сильные стороны

- Laravel API организован вокруг контроллеров, моделей, Request/Resource-классов и сервисов.
- Используются миграции и Eloquent-связи.
- Для расписания есть отдельный `ScheduleLessonService` с проверкой конфликтов.
- Для импорта есть единая история `import_jobs`, preview, mapping, validation и confirm.
- Для аудита есть централизованный `AuditLogService`.
- Для настроек есть `SettingService`.
- Для справочников есть `ReferenceService` и Reference Data Platform.
- Тестовый контур покрывает основные API: текущий suite после DATA-002 содержит 165 тестов и 771 assertion.

### Риски

- `UniversalImportService` стал слишком большим: около 60 KB, содержит парсинг CSV/XLSX, описание типов, mapping, validation, бизнес-resolve, шаблоны и confirm-логику.
- Часть старых CSV-сервисов остается рядом с универсальным импортом. Это создает два параллельных подхода к импорту.
- Некоторые контроллеры содержат импорт/экспорт и domain actions одновременно, например Exam, Graduate, Curriculum, TeachingLoad.
- RBAC существует, но значительная часть CRUD сгруппирована под широким `manage_dictionaries`, что недостаточно точно для реальной эксплуатации.
- Person/Identity концептуально описан, но в коде пока используются отдельные `Student`, `Teacher`, `Graduate`, `Applicant` и `User` с временными связями.

## Frontend

### Сильные стороны

- Новый GUI построен на Quasar + Tailwind + Lucide согласно ADR-001.
- Есть layouts, router, Pinia stores, UI Foundation components.
- Основные модули уже перенесены в новый интерфейс.
- Есть единые паттерны: таблица + карточка справа, фильтры, status badges, confirm dialogs.
- Legacy остается доступным, что снижает риск миграции.

### Риски

- `frontend/src/App.vue` остается очень крупным legacy-файлом около 133 KB.
- Несколько новых страниц также стали крупными: Graduation, Exams, Users, UniversalImport, Curricula, Admissions, TeachingLoad.
- Router содержит много прямых импортов страниц. Это увеличивает initial bundle и подтверждается build warning о chunk больше 500 KB.
- Часть страниц повторяет CRUD-паттерны вручную вместо общего composable/page factory.
- Dashboard и Mobile Student частично используют mock-данные, что нужно заменить реальными API по мере зрелости модулей.

## Сервисы

### Хорошо

- `AuditLogService`, `SettingService`, `ReferenceService`, `ScheduleLessonService`, `AutoCodeService` имеют понятную ответственность.
- Есть возможность расширять сервисы без изменения API.

### Требует внимания

- `UniversalImportService` нужно разделить на импорт-пайплайн и отдельные target handlers.
- CSV-сервисы старых модулей нужно постепенно привести к единому механизму универсального импорта или явно оставить как legacy import/export.
- SearchService на frontend большой и будет расти при добавлении сущностей.

## Модели

Модельный слой покрывает основные домены MVP. Сильная сторона: большинство сущностей лежат в стандартном Eloquent-слое, миграции описывают связи и индексы.

Риск: центральный `Person` пока не реализован как кодовая сущность. Из-за этого фото, роли, QR и мобильный кабинет вынуждены связываться с конкретными типами владельцев. Это приемлемо для MVP, но дальнейшее развитие Identity лучше вести через единый Person/Party слой.

## Импорт

После DATA-002 `/admin/import` поддерживает:

- students;
- groups;
- teachers;
- subjects;
- classrooms;
- applicants;
- curricula;
- teaching-load;
- schedule.

Архитектура импорта функциональна: preview, mapping, validation, confirm, история, шаблоны. Главный долг: слишком много ответственности в одном классе. Следующий шаг — Strategy/Handler по типам данных.

## Identity, QR и Access

Identity/QR/Access реализованы как MVP:

- `digital_identities` с token без персональных данных;
- QR-выдача и отзыв;
- `access_events`;
- проходная `/access/gate`;
- отчеты `/access/reports`.

Архитектурно направление верное. Требуется довести роли access-оператора, TTL/rotation токенов, отдельные политики доступа, аудит сканирования и привязку к будущей Person.

## Mobile

Мобильный кабинет студента реализован как MVP. Архитектурно это отдельный layout и маршруты `/m/student`, `/m/student/pass`. Подход правильный, но данные пока не полностью персонализированы через зрелую Identity/Person модель.

## Audit

Audit Platform уже централизована и подключена к важным действиям. Следующий уровень зрелости:

- единый request_id на каждый запрос;
- больше automated observers;
- retention policy;
- экспорт/архивация audit logs;
- защита audit от изменения.

## Settings

Settings Center создан правильно: системные параметры ушли из `.env`/сидеров в управляемый раздел. Важное правило остается: секреты не хранить plain text. Нужно расширять список публичных настроек осторожно.

## Reference Data

Reference Data Platform — правильная основа для российского СПО: статусы, формы обучения, виды занятий, виды нагрузки, статусы дипломов и заявлений. Уже есть начальная интеграция в Students, Admissions, Exams, Teaching Load и Graduation. Следующий шаг — довести использование справочников до всех форм и импортов.

## Итог

Архитектура Release 0.7 пригодна для пилотной загрузки данных и UAT. До промышленной эксплуатации нужно снизить технический долг в импорте, frontend bundle, RBAC и Person/Identity. Рекомендуется не делать большой rewrite, а идти малыми refactor tasks с сохранением API и поведения.
