# PRODUCTION_DEPLOYMENT_READINESS

Дата: 09.07.2026.  
Окружение подготовки: DEV `/srv/college-dev`.  
PROD: не изменялся.

## Цель

Документ оценивает готовность CollegePortal к будущему безопасному переносу из DEV в PROD. Он не разрешает деплой сам по себе: фактический PROD-deploy должен выполняться отдельной задачей после ручного подтверждения.

## Что уже готово

### Архитектура и функциональность

- Новый Quasar GUI работает поверх существующего Laravel API.
- Legacy `/legacy` сохранен.
- Основные модули Release 0.7 реализованы и доступны в DEV.
- Универсальный импорт поддерживает реальные данные: students, groups, teachers, subjects, classrooms, applicants, curricula, teaching-load, schedule.
- Import handlers выделены из `UniversalImportService`.
- Frontend routes переведены на lazy loading, основной JS chunk уменьшен.

### Администрирование

- Есть users/roles foundation.
- Есть Settings Center.
- Есть Reference Data Platform.
- Есть Audit Log Platform.
- Есть production-защита очистки demo-data.
- Есть документация по DEV/PROD и safe deployment scripts.

### Проверки качества

- Backend test suite регулярно проходит в DEV.
- Frontend build проходит в DEV.
- Smoke-check ключевых маршрутов проходит в DEV.
- Документация Release 0.7 и UAT подготовлена.

## Что нужно проверить вручную

### Окружение

- [ ] PROD path и docker compose соответствуют документации.
- [ ] PROD `.env` заполнен production-значениями.
- [ ] `APP_ENV=production`, `APP_DEBUG=false`.
- [ ] PROD database отдельная от DEV.
- [ ] PROD ports не конфликтуют с DEV.

### Доступы

- [ ] Созданы реальные production-пользователи.
- [ ] Demo users удалены, заблокированы или сменили пароли.
- [ ] Проверены роли и permissions.
- [ ] Администратор, учебная часть, приемная комиссия, преподаватель, студент и проходная видят только нужные разделы.

### Данные

- [ ] Справочники согласованы с колледжем.

- [ ] Есть план переноса или повторной загрузки данных в PROD.

### Инфраструктура

- [ ] HTTPS настроен.

- [ ] Backup/restore проверены.

## Что блокирует перенос в PROD

Перенос в PROD нельзя выполнять, если есть хотя бы один пункт:

- нет свежего backup PostgreSQL;
- `APP_DEBUG=true`;
- PROD использует DEV database;
- demo/admin пароли не сменены;
- HTTPS не настроен для внешнего доступа;
- неизвестно, где хранятся загруженные import-файлы с персональными данными;
- роли пользователей не проверены;
- `/admin/import` доступен лишним ролям;
- `php artisan test` или `npm run build` падает;
- нет rollback plan;
- пользователь не подтвердил реальный деплой отдельно.

## Rollback plan

### Перед деплоем

1. Зафиксировать commit hash DEV, который планируется деплоить.
2. Создать backup файлов PROD.
3. Создать backup PostgreSQL PROD.
4. Сохранить backup в утвержденной папке, например `/srv/backups/college-portal/`.
5. Проверить наличие места на диске.
6. Записать текущие версии контейнеров и образов.

### Если деплой неуспешен

1. Остановить новые PROD контейнеры.
2. Вернуть файлы проекта из backup.
3. Восстановить PostgreSQL из backup, если миграции или данные были затронуты.
4. Запустить старые PROD контейнеры.
5. Проверить `/login`, `/dashboard`, `/legacy` и API login.
6. Зафиксировать incident report.

### Если ошибка обнаружена после запуска

1. Оценить, затронуты ли данные пользователей.
2. Если затронуты только файлы frontend/backend, откатить код на предыдущий commit.
3. Если затронута БД, остановить запись данных и восстановить backup.
4. Сообщить пользователям о техническом окне, если PROD уже используется.
5. Не выполнять повторный деплой без нового checklist.

## Итоговая оценка

CollegePortal в DEV технически готовится к будущему PROD, но перенос должен быть заблокирован до ручной проверки production `.env`, HTTPS, backup/restore, ролей, demo-паролей, retention import-файлов и результатов пилотной загрузки реальных данных.
