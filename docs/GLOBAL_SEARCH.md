# Global Search CollegePortal

## 1. Общая архитектура поиска

Глобальный поиск CollegePortal строится как frontend-фундамент поверх существующих REST API. На этапе GUI-006 backend, база данных и API endpoints не меняются.

Слои поиска:

- `GlobalSearch.vue` — строка поиска в верхней панели и выпадающий список результатов;
- `stores/search.js` — состояние поиска, последние результаты, история запросов, выбранный результат;
- `services/searchService.js` — единый интерфейс `search(query)` и нормализация результатов разных сущностей;
- существующие API ресурсов — источник данных для первых провайдеров поиска.

Целевой принцип: каждый модуль подключает свой search provider, который знает, какие endpoint использовать, какие поля читать и как привести результат к единому формату.

Единый формат результата:

```js
{
  id: 1,
  type: 'student',
  group: 'Студенты',
  title: 'Иванов Иван Иванович',
  subtitle: 'ИСП-101 · Обучается',
  meta: ['Телефон', 'Email'],
  route: { path: '/students', query: { selected: 1 } },
  entity: {}
}
```

## 2. Сущности поиска

Поиск должен поддерживать:

- Студенты;
- Группы;
- Преподаватели;
- Дисциплины;
- Аудитории;
- Расписание;
- Журнал;
- Абитуриенты;
- Документы;
- Отчеты.

На этапе GUI-006 реализованы только frontend-провайдеры для студентов и групп.

## 3. Индексируемые поля

### Студенты

- фамилия;
- имя;
- отчество;
- группа;
- телефон;
- email;
- статус;
- дата зачисления.

### Группы

- название группы;
- курс;
- год набора;
- специальность;
- образовательная программа;
- форма обучения;
- куратор.

### Преподаватели

- фамилия;
- имя;
- отчество;
- телефон;
- email;
- статус активности;
- закрепленные дисциплины, если доступны.

### Дисциплины

- название;
- код;
- краткое наименование;
- связанные программы, если доступны.

### Аудитории

- номер;
- корпус;
- тип аудитории;
- вместимость;
- оборудование, если доступно.

### Расписание

- дата;
- время;
- группа;
- дисциплина;
- преподаватель;
- аудитория;
- тема занятия.

### Журнал

- группа;
- дисциплина;
- занятие;
- студент;
- оценка;
- посещаемость;
- дата.

### Абитуриенты

- фамилия;
- имя;
- отчество;
- телефон;
- email;
- специальность;
- образовательная программа;
- статус заявления.

### Документы

- номер;

- период;
- тип отчета;
- дата формирования.

## 4. Отображение результатов

Каждый результат должен показывать:

- тип сущности;
- основное название;
- вторичную строку с контекстом;
- компактные метаданные, если они помогают отличить записи;
- действие перехода к карточке или разделу.

Результаты не должны выглядеть как отдельные карточки с тяжелыми рамками. Для рабочего интерфейса колледжа подходит плотный список с разделителями и группировкой.

## 5. Группировка результатов

Результаты группируются по типам сущностей:

- Студенты;
- Группы;
- Преподаватели;
- Дисциплины;
- Аудитории;
- Расписание;
- Журнал;
- Абитуриенты;
- Документы;
- Отчеты.

В каждой группе показывается ограниченное количество результатов. Если результатов больше лимита, позже можно добавить действие «Показать все в разделе».

## 6. Быстрые действия из результатов

Минимальный набор действий:

- открыть карточку студента;
- открыть карточку группы;
- перейти к списку с примененным фильтром;
- открыть связанную сущность, если это поддерживает раздел.

Будущие действия:

- открыть карточку преподавателя;
- открыть занятие в расписании;
- открыть запись журнала;
- открыть заявление абитуриента;
- открыть документ;
- сформировать или открыть отчет.

## 7. Подключение новых модулей

Чтобы подключить новый модуль:

1. Добавить provider в `frontend/src/services/searchService.js`.
2. Описать загрузку данных через существующий API.
3. Указать поля для поиска и нормализации.
4. Вернуть результат в едином формате.
5. Добавить группу результата и маршрут перехода.
6. При необходимости научить страницу читать query-параметр выбора записи.

Provider не должен знать о внутреннем состоянии Vue-компонентов. Он только получает данные, фильтрует или запрашивает их и возвращает нормализованный результат.

## Текущие ограничения GUI-006

- Поиск выполняется только по студентам и группам.
- Backend-поисковый индекс не создается.
- Ранжирование простое: сначала точные и частичные совпадения в основных полях, затем остальные найденные записи.
- Поиск предназначен для небольшого MVP-набора данных. При росте объема нужно перенести индексирование на backend.
