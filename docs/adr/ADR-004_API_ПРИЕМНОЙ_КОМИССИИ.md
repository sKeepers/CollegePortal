# ADR-004: API подсистемы «Приемная комиссия»

## Статус

Принято для ADM-003 API and process foundation.

## Контекст

ADM-001 зафиксировал архитектурные границы подсистемы «Приемная комиссия». ADM-002 зафиксировал нормализованную модель данных с Person, Applicant, Application, выбранными специальностями, документами, достижениями, экзаменами, конкурсами, приказами и зачислениями.

Нужно спроектировать API так, чтобы будущая реализация могла развиваться поэтапно и не смешивала CRUD заявления с конкурсом, приказами, зачислением и ФИС.

## Решение

Использовать REST API с базовым префиксом:

```text
/api/admissions
```

API делится на области:

- applicants;
- applications;
- choices;
- documents;
- completeness;
- achievements;
- exams;
- competitions;
- orders;
- enrollments;
- FIS packages;
- reference;
- events.

Критичные операции выполняются отдельными командами, а не скрытыми side effects обычного `PUT`:

- регистрация заявления;
- отзыв заявления;
- проверка документа;
- пересчет рейтинга;
- рекомендация;
- утверждение приказа;
- preview/apply зачисления;
- создание ФИС-пакета.

## Причины

### Разные жизненные циклы

Заявление, документ, конкурс, приказ и зачисление имеют разные правила изменения. Один универсальный CRUD endpoint быстро станет неуправляемым.

### Явные бизнес-команды

Регистрация, рекомендация, утверждение приказа и зачисление являются бизнес-событиями. Они должны иметь отдельные endpoints, permissions, audit и подтверждение.

### Preview -> apply

Зачисление и ФИС-пакеты могут менять много данных или формировать юридически значимый результат. Для них нужен предварительный отчет, request_id и идемпотентность.

### RBAC на backend

Frontend может помогать UX, но только backend решает, можно ли выполнить действие. Поэтому permissions указаны на уровне каждого endpoint.

### Интеграционный слой ФИС

ФИС не должен управлять внутренними заявлениями напрямую. API приемной комиссии готовит снимок данных, а transport остается в integration layer.

## Альтернативы

### Один `/api/admissions` controller для всего

Отклонено. Он смешивает создание заявления, документы, конкурс, приказы, зачисление и ФИС, что ухудшает RBAC, audit и тестируемость.

### Все изменения через `PUT /applications/{id}`

Отклонено. Такой подход скрывает бизнес-события и усложняет подтверждения, историю и права доступа.

### Выполнять зачисление сразу из утверждения приказа

Отклонено. Утверждение приказа и создание студента являются разными действиями. Между ними нужен preview, проверка дублей и участие учебной части.

### Встроить отправку ФИС в API заявления

Отклонено. ФИС имеет отдельные контракты, validation, статусы обмена и stop-gates. CRUD заявления не должен выполнять transport во внешний контур.

## Последствия

Положительные:

- будущая реализация может идти по этапам;
- permissions легко проверять и тестировать;
- audit получает точные события;
- критичные операции имеют подтверждение;
- зачисление защищено от дублей;
- ФИС остается изолированным integration layer.

Ограничения:

- endpoints больше, чем у простого CRUD;
- потребуется дисциплина в naming permissions;
- frontend должен учитывать доступные действия из backend response;
- implementation требует сервисного слоя, а не тонких CRUD controllers.

## Подготовка к ADM-004

ADM-004 рекомендуется посвятить миграционной и implementation-стратегии первого backend slice:

1. Reference Data для статусов, типов документов и permissions;
2. read-only endpoints для справочников и списка заявлений;
3. Applicant/Application create/update без разрушения текущего `/admissions`;
4. базовый audit событий заявления;
5. тесты RBAC 403/200;
6. обратная совместимость текущего UI.
