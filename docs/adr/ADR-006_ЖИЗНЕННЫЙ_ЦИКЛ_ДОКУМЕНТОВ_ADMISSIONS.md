# ADR-006: Жизненный цикл документов Admissions Foundation

Дата: 2026-07-26

Статус: принято для BACK-005.1.

## Контекст

BACK-005 создал foundation документов абитуриента: документы личности, документы об образовании, private-файлы, СНИЛС и readiness. Аудит BACK-005 показал два риска:

- конкретное заявление не фиксировало, какой документ использовался при регистрации;
- PATCH реквизитов документа мог изменить историческую запись на месте.

Для приемной комиссии это опасно: зарегистрированное заявление должно воспроизводиться через месяцы и годы, даже если у Applicant позже появился новый паспорт, новый аттестат или исправленная версия документа.

## Решение

Использовать минимальную явную связь:

- `admission_application_documents.application_id`;
- `admission_application_documents.identity_document_id`;
- `admission_application_documents.education_document_id`.

Документы получают version chain:

- `previous_version_id`;
- `version_number`;
- `replaced_by_document_id`;
- `replaced_at`.

Правила:

- read-only запросы не создают link-row;
- при регистрации заявления сервис фиксирует текущие основные документы, если связь не задана вручную;
- зарегистрированное заявление не позволяет заменить закрепленный документ другой записью;
- изменение реквизитов закрепленного документа создает новую версию;
- старая версия остается связанной с зарегистрированным заявлением;
- изменение статуса проверки и служебного комментария может выполняться на месте;
- файлы закрепленного документа зарегистрированного заявления не изменяются и не архивируются обычным flow;
- private files физически не удаляются в рамках BACK-005.1.

Для документа об образовании добавлены только поля, подтвержденные локальной XSD ФИС 4.9:

- `qualification_name`;
- `speciality_name`;
- `registration_number`;
- `is_nostrificated`.

Словарные соответствия ФИС проверяются через существующую таблицу `fis_external_mappings`. Внутренние ID `reference_items` не считаются кодами ФИС.

## Альтернативы

### Snapshot всех реквизитов в JSON заявления

Отклонено. Такой подход быстро превращает заявление в невалидируемую копию документа, усложняет masked resources, audit и будущий экспорт.

### Foreign keys прямо в `applicant_applications`

Отклонено для текущего этапа. `applicant_applications` является переходной таблицей, где legacy и foundation записи изолируются через `record_type`. Отдельная link table безопаснее для эволюции и не расширяет legacy surface.

### Immutable documents без новых версий

Отклонено. Приемная комиссия должна иметь возможность исправить реквизиты или принять новый документ Applicant без потери истории старого заявления.

## Последствия

Плюсы:

- зарегистрированное заявление воспроизводимо;
- readiness использует именно документы заявления;
- новая версия документа не меняет историю старого заявления;
- FIS readiness не смешивает внутренние справочники и внешние коды;
- API расширен additive и не ломает BACK-005 endpoints.

Минусы:

- frontend должен показывать версии и закрепленные документы;
- новые версии не получают файлы автоматически;
- полноценная retention policy и cleanup остаются отдельной задачей;
- ФИС XML/export state machine не реализуются в этом ADR.

## Граница с ФИС

BACK-005.1 не создает XML, не выполняет XSD validation полного пакета, не вызывает SOAP/Gateway и не отправляет данные в ФИС. Решение только готовит доменную модель и readiness к будущему FIS mapping.
