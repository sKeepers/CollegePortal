# ADR-002: Архитектура подсистемы «Приемная комиссия»

## Статус

Принято для архитектурного foundation ADM-001.

## Контекст

CollegePortal развивается как модульная информационная система колледжа. Первая функциональная подсистема должна показать подход к построению доменных модулей: отдельные сущности, сервисный слой, защищенный API, Quasar GUI, RBAC, Audit, Reference Data и интеграции без смешивания бизнес-логики.

Подсистема «Приемная комиссия» находится на границе нескольких доменов:

- `Identity`: физическое лицо, пользователь, Person, дубли;
- `Academic`: специальности, образовательные программы, будущие группы;
- `Administration`: заявления, документы, конкурс, приказы;
- `Integrations`: ФИС ГИА и Приема;
- `Analytics`: Dashboard, контроль комплектности, отчеты.

Нужно зафиксировать архитектуру так, чтобы дальнейшие этапы можно было реализовывать постепенно: сначала CRUD, затем документы, конкурс, приказы, ФИС и личный кабинет абитуриента.

## Решение

Выделить «Приемную комиссию» как отдельный модуль домена `Administration`.

Архитектурная модель:

```text
Person
  -> Applicant Application
      -> Documents
      -> Events
      -> Competition
      -> Order
      -> Enrollment -> Student
      -> FIS Package
```

Backend должен строиться вокруг отдельных controllers, requests, resources и services для заявлений, документов, событий, конкурса, приказов и интеграций. Frontend должен использовать отдельную страницу `/admissions`, store и специализированные панели формы, фильтров и карточки заявления.

ФИС не должен быть частью CRUD заявлений. Для ФИС используется отдельный integration layer: импорт, подготовка пакетов, validation, обмен через Gateway и журнал коммуникаций.

## Почему выбрана такая архитектура

1. Приемная комиссия работает с персональными данными, поэтому ей нужны четкие границы доступа, audit и приватное хранение файлов.
2. Абитуриент может стать студентом и выпускником, поэтому модуль должен быть связан с `Person`, а не жить как изолированная таблица заявлений.
3. Конкурс, приказы и ФИС имеют разные жизненные циклы. Их нельзя смешивать в одном CRUD-контроллере.
4. Reference Data снижает риск строковых констант в статусах, типах документов и формах обучения.
5. Отдельный integration layer позволяет развивать ФИС без переписывания приемной комиссии и без риска случайной production-отправки.
6. Workspace/UI pattern дает сотруднику приемной комиссии один предсказуемый рабочий экран: список, фильтры, карточка, документы, история и действия.

## Взаимодействие с другими подсистемами

### Identity и Person

Модуль использует `Person` для поиска дублей, связи с будущим студентом и консолидации ФИО, контактов и фото. Автоматическое объединение по одному ФИО запрещено.

### Academic

Заявление ссылается на специальность и образовательную программу. Зачисление использует группы и будущий учебный контур.

### Students

После приказа абитуриент переводится в студенты. Операция должна быть идемпотентной и проверять, что студент уже не создан ранее.

### Reference Data

Типы документов, статусы, формы обучения, формы финансирования и основания поступления должны храниться в справочниках.

### RBAC

Минимальная модель permissions:

- `admissions.view`;
- `admissions.edit`;
- `admissions.documents.*`;
- `admissions.bulk_*`;
- будущие `admissions.competition.*`;
- будущие `admissions.orders.*`;
- будущие `admissions.portal.*`.

### Audit

Все изменения заявления, документов, конкурсных решений, приказов, импортов и экспортов пишутся в Audit. Содержимое файлов, паспортные данные, СНИЛС и raw payload ФИС не пишутся в audit payload.

### ФИС

ФИС получает подготовленный пакет данных из приемной комиссии, но не управляет внутренней моделью заявления напрямую. Обмен с TEST/PROD контурами ФИС должен идти только через официальные контракты и отдельные stop-gates.

## Последствия

Положительные:

- модуль можно развивать по этапам без большого rewrite;
- зачисление связывается с контингентом и Person;
- документы и ФИС не смешиваются с CRUD заявлений;
- audit и RBAC проектируются сразу;
- будущий личный кабинет абитуриента получает понятную backend-основу.

Ограничения:

- больше доменных сервисов и документов, чем у простого CRUD;
- требуется дисциплина в Reference Data;
- конкурс и приказы нельзя реализовать как набор быстрых полей в заявлении;
- ФИС-интеграция остается отдельным архитектурным потоком.

## Альтернативы

### Один CRUD заявлений без отдельного домена

Отклонено. Быстро на старте, но плохо масштабируется на документы, конкурс, приказы, ФИС и Person.

### Хранить документы как флаги в заявлении

Отклонено. Невозможно надежно учитывать типы документов, файлы, проверку, отклонения, audit и будущую выгрузку.

### Встроить ФИС прямо в Admission controller

Отклонено. Интеграционные контракты, transport, validation и статусы обмена должны быть изолированы от внутренней бизнес-модели.

## Проверки для будущих этапов

- backend API защищен permissions;
- frontend скрывает действия без permissions, но источником истины остается backend;
- документы хранятся в private storage;
- audit не содержит персональные payload;
- импорт имеет preview/dry-run/apply;
- зачисление не создает дублей;
- ФИС production endpoint не используется без отдельной задачи.
