# ADR-005: Стратегия реализации подсистемы «Приемная комиссия»

## Статус

Принято для ADM-004 implementation strategy foundation.

## Контекст

ADM-001 описал архитектуру подсистемы «Приемная комиссия». ADM-002 зафиксировал модель данных. ADM-003 зафиксировал REST API, RBAC и бизнес-процессы. Следующий шаг перед кодом - определить, как именно реализовывать backend и frontend без большого rewrite и без риска сломать существующий `/admissions`.

## Решение

Реализовывать подсистему эволюционно через небольшие задачи и layered architecture:

```text
Frontend Workspace
  -> API Controllers / Requests / Resources
    -> Application Use Cases
      -> Domain Services
        -> Repositories
          -> Database / Private Storage / Audit / Reference Data
```

Порядок реализации:

1. Reference Data, statuses и permissions.
2. Applicant и Person linking.
3. Application foundation.
4. Choices и completeness.
5. Documents registry и private files.
6. Achievements и exams.
7. Competitions.
8. Orders.
9. Enrollment.
10. FIS package snapshot.
11. Frontend slices поверх стабильных backend slices.

## Причины

### Эволюционный переход

Текущий `/admissions` уже существует. Большой rewrite повысит риск регрессий, поэтому новый foundation должен внедряться слоями и сохранять обратную совместимость.

### Сервисный слой вместо тонкого CRUD

Приемная комиссия содержит юридически значимые действия: регистрация заявления, проверка документов, рекомендация, приказ и зачисление. Эти действия нельзя надежно реализовать как обычный CRUD без use cases, Audit и RBAC.

### Preview -> apply

Зачисление и ФИС-пакеты могут менять много данных или создавать официальный результат. Предварительный отчет и идемпотентность снижают риск ошибок.

### Private storage

Документы абитуриентов содержат персональные данные. Они должны храниться отдельно от публичных assets и скачиваться только через backend.

### Staged frontend

Frontend должен подключаться после стабилизации backend endpoints. Это снижает риск временных заглушек и расхождения UI с бизнес-правилами.

## Альтернативы

### Реализовать весь модуль одним большим PR

Отклонено. Такой PR будет трудно ревьюить, тестировать и откатывать.

### Начать с frontend-макетов

Отклонено. Без backend contracts и permissions UI быстро начнет зашивать временную бизнес-логику.

### Сразу заменить текущий `/admissions`

Отклонено. Нужно сохранить текущий рабочий раздел до завершения migration/backfill и smoke.

### Хранить документы в public storage

Отклонено. Документы абитуриентов не должны быть доступны как публичные статические файлы.

## Последствия

Положительные:

- реализацию можно делить на маленькие PR;
- снижается риск регрессии текущего `/admissions`;
- Audit и RBAC проектируются до UI;
- миграции можно проверять dry-run/backfill;
- frontend получает стабильные API contracts.

Ограничения:

- реализация займет больше итераций;
- временно будут сосуществовать старые и новые структуры;
- потребуется дисциплина в документации переходных состояний;
- часть frontend-функций появится только после backend foundation.

## Подготовка к первым задачам

Первый кодовый этап должен начинаться с `BACK-001`:

- Reference Data;
- permissions;
- роли по умолчанию;
- минимальные tests;
- отсутствие изменений frontend.

После `BACK-001` можно переходить к `BACK-002` и `BACK-003`, сохраняя текущий `/admissions` совместимым.
