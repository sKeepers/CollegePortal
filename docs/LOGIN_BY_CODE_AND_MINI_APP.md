# Вход по коду из бота и вход из мини-приложения

Два способа входа, сделанных по решению владельца 17.08.2026. Оба живут на той же форме входа и выдают ту же сессию, что и вход паролем, — cookie `cp_session` с признаком CSRF.

Общее правило, которое не меняется ни для одного способа: **учётная запись не создаётся никогда**. Нет привязанного мессенджера — нет входа.

## Вход по коду

Человек вводит логин, нажимает «Войти по коду из бота» → «Получить код», получает шесть цифр в мессенджер и вводит их. Пароль не участвует.

**Что нужно, чтобы это работало у конкретного человека:**

1. в разделе «Моя учётная запись» привязан мессенджер;
2. человек нажал у бота «Старт» — **бот не может написать первым**, и без начатого диалога писать некуда;
3. на портале задан токен бота этого мессенджера.

Сегодня доставка есть только у **MAX**. Канал Telegram не реализован не по забывчивости: замер 11.08.2026 показал, что с боевого сервера его API отвечает через раз — DNS отдаёт адреса по кругу, режет вышестоящий провайдер. Код от канала не зависит и пойдёт через Telegram в тот день, когда канал появится.

**Ответ на запрос кода одинаков всегда** — и когда логина нет, и когда мессенджер не привязан, и когда отправить не удалось. Это сделано нарочно: иначе форма входа превращается в способ перебирать учётные записи колледжа и заодно узнавать, у кого привязан мессенджер. Что произошло на самом деле, видно в журнале аудита (`login_code_sent`, `login_code_no_channel`, `login_code_send_failed`, `login_code_refused`, `login_code_burned`).

**Защита в три слоя,** потому что шесть цифр перебираются:

| Слой | Порог |
| --- | --- |
| запросов кода | 2 в минуту на логин, 20 в минуту с адреса |
| проверок кода | 5 в минуту на логин, 60 в минуту с адреса |
| сам код | сгорает после 5 неверных попыток |

Код живёт 5 минут, одноразовый, живым бывает только один: новый запрос гасит прежний. В базе лежит отпечаток, а не сам код — как у пароля.

## Вход из мини-приложения

Портал, открытый **внутри** Telegram или MAX, входит сам: мессенджер передаёт подписанные данные запуска, сервер проверяет подпись ключом бота и находит привязку.

Кнопки у этого способа нет и не будет: снаружи мини-приложения данных запуска не существует. Если портал открыт в обычном браузере, человек просто видит обычную форму.

**Подпись проверяется только на сервере, и сервер никуда не ходит** — ни в `api.telegram.org`, ни в MAX. Проверка целиком локальная: иначе вход ломался бы вместе с чужой доступностью.

Данные запуска считаются свежими 15 минут. Подпись верна вечно, ограничивает только `auth_date`.

### Ловушка, на которой легко потерять день

Ключ и сообщение в HMAC у мини-приложения **переставлены местами** по сравнению с виджетом входа:

| Способ | Ключ HMAC | Сообщение |
| --- | --- | --- |
| Login Widget (Telegram) | `SHA256(токен бота)` | строка проверки данных |
| Мини-приложение (Telegram и MAX) | строка `"WebAppData"` | **токен бота** |

Перепутать легко, а ошибка тихая: подпись просто никогда не сходится, и выглядит это как «вход сломан». Закреплено тестом `the widget signing rule is not accepted`.

### Привязка одна на мессенджер

Человек привязывает **мессенджер**, а не способ входа. Поэтому привязка хранится под кодом `telegram` или `max`, а входов к ней ведёт два — виджет и мини-приложение. У провайдера для этого есть `identityCode()`, отдельный от `code()`.

## Чего не хватает: регистрация на стороне мессенджеров

**Портальная часть готова целиком, но открыть мини-приложение пока неоткуда.** Это делается в кабинете каждой площадки и требует владельца:

| Площадка | Что сделать |
| --- | --- |
| Telegram | у бота через BotFather задать Web App / Menu Button с адресом `https://portal.skki.ru` |
| MAX | на площадке разработчика зарегистрировать мини-приложение с тем же адресом и кнопкой `open_app` у бота |

Адрес обязан быть **боевым доменом**: обе площадки открывают только `https` с доверенным сертификатом, поэтому на стенде `192.168.34.114:5443` мини-приложение не проверяется в принципе.

**Живой проверки не было** — ни у Telegram, ни у MAX: без регистрации приложения открыть его негде. Проверено то, что проверяется без площадки: разбор данных запуска, проверка подписи, отказ подделке, отказ просроченным данным, отказ непривязанному, отказ подписи по правилу виджета.

Отдельно про MAX: его клиентская библиотека отдаёт данные запуска в `window.WebApp.initData`. Портал берёт их **строкой** — в том виде, в каком их подписывали. Если внутри приложения там окажется разобранный объект, а не строка, вход не состоится и это будет видно сразу; чинится это одной строкой на форме входа, но угадывать заранее, в каком виде MAX их отдаёт, не стоит.

## Что проверить первым, когда приложения зарегистрируют

1. Открыть портал из мессенджера человеком, у которого привязка **есть** — должен войти сам.
2. Тем же способом человеком, у которого привязки **нет** — должен увидеть обычную форму, без сообщения об ошибке.
3. Войти по коду: запросить, получить, ввести. Затем ввести тот же код второй раз — должен получить отказ.
4. Запросить код на несуществующий логин — сообщение обязано быть тем же самым.
