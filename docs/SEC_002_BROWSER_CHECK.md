# Проверка SEC-002: токен сессии в httpOnly cookie

Задача закрыта коммитом `cc343c544`, документ — результат проверки на DEV и список шагов для владельца.

Смысл проверки: смена схемы авторизации на PROD **разлогинит всех**, и если она при этом сломана, входа обратно не будет. Поэтому сначала стенд.

## Что проверено автоматически

Скрипт [scripts/deploy/check-auth-cookie.sh](../scripts/deploy/check-auth-cookie.sh) — запускать из корня установки на стенде, пароль он берёт из `backend/.env` и не печатает:

```bash
bash scripts/deploy/check-auth-cookie.sh
```

Проверено на DEV 10.08.2026, все пункты сошлись:

| Что | Ожидалось | Получено |
| --- | --- | --- |
| Токена нет в теле ответа на вход | нет | нет, `token_type: Cookie` |
| `cp_session` помечена `HttpOnly` | да | да |
| `cp_csrf` доступна из JavaScript | да | да, она и нужна фронтенду |
| Чтение по cookie и после обновления страницы | 200 | 200 |
| Изменение без признака CSRF | 419 | 419 |
| Изменение с чужим признаком | 419 | 419 |
| Истёкший токен | 401 | 401 |
| Выход с верным признаком | 200 | 200 |
| Обращение после выхода | 401 | 401 |

Отдельно проверен мобильный контур на уровне запросов:

| Что | Результат |
| --- | --- |
| QR-пропуск, `Accept: image/svg+xml`, по cookie | 200 |
| QR-пропуск, `Accept: image/png`, по cookie | 200 |
| Тот же запрос без cookie | 401 |
| `POST access/scan` без признака CSRF | 419 |
| `POST access/scan` с признаком | до проверки прав доходит, CSRF пропускает |

Автоматические тесты: `CookieSessionTest` — девять случаев, включая недоступность токена из JavaScript, отказ без признака и с чужим признаком, истёкший токен, вход, выход и продление. Весь набор — 505 на SQLite и на PostgreSQL 17.

## Что должен посмотреть человек

Запросами нельзя проверить поведение интерфейса и камеру телефона. Это остаётся за владельцем.

**Адрес стенда:** `https://192.168.34.114:5443` изнутри сети, `https://84.54.208.134:5443` снаружи. Учётные записи — в [TEST_USERS.md](TEST_USERS.md), пароль общий.

**Важно:** все, кто был залогинен на DEV до выкатки, разлогинены. Это ожидаемо — надо войти заново.

### На компьютере

1. Войти под любой учётной записью. **Галочку «не выходить из сайта на этом устройстве» снять.** Портал должен открыться.
2. Нажать F12, вкладка Console, выполнить:
   ```js
   localStorage.getItem('college_portal_token')   // ожидается null
   sessionStorage.getItem('college_portal_token') // ожидается null
   document.cookie                                // cp_session здесь быть НЕ должно
   ```
   В `document.cookie` видны `cp_csrf` и `cp_persist` — так и задумано, секрета они не несут. Отсутствие `cp_session` в этом списке и есть то, ради чего задача делалась.
3. Обновить страницу (F5) — портал остаётся открытым, повторный вход не требуется.
4. Что-нибудь сохранить: например, открыть «Люди», выбрать человека, «Изменить данные», сохранить. Должно сохраниться без ошибок — это изменяющий запрос, и он идёт с признаком CSRF.
5. Закрыть браузер целиком и открыть заново на том же адресе. Так как галочка была снята, портал должен спросить вход.
6. Войти снова, **теперь галочку поставить**, закрыть и открыть браузер — портал должен остаться открытым.
7. Выйти через меню. Портал возвращает на форму входа, и кнопка «назад» в браузере не должна вернуть внутрь.

### На телефоне

Обе страницы требуют защищённого соединения, поэтому только по `https`.

8. Открыть `https://84.54.208.134:5443` (или адрес внутри сети), войти.
9. Открыть «Проходная» → «Сканер» (`/access/mobile-scanner`). Разрешить доступ к камере. Камера должна включиться, а наведение на QR — давать ответ о результате прохода. **Это главный пункт: сканер ходит тем же входом, и именно он мог пострадать от смены схемы.**
10. Открыть свой цифровой пропуск (`/identity/digital-passes`, строка пропуска, кнопка показа QR). Код должен отобразиться. На стенде для этого выпущен пропуск сотрудника — он там уже есть.

### Если что-то не сошлось

Сообщите, что именно и на каком шаге. Правка на моей стороне: задача считается закрытой только после этих шагов.

## На PROD не разворачивалось

Выкатка разлогинит всех, кто там работает. Отдельное поручение обязательно. Порядок обычный: собрать релиз на DEV, обновить PROD установщиком, сразу после обновления прогнать `scripts/deploy/check-auth-cookie.sh` на боевом адресе и войти в браузере под одной учётной записью, прежде чем расходиться.
