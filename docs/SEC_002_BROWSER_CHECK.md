# Проверка SEC-002: токен сессии в httpOnly cookie

Задача закрыта коммитом `cc343c544`, документ — результат проверки на DEV и список шагов для владельца.

Смысл проверки: смена схемы авторизации на PROD **разлогинит всех**, и если она при этом сломана, входа обратно не будет. Поэтому сначала стенд.

## Что проверено автоматически

Скрипт [scripts/deploy/check-auth-cookie.sh](../scripts/deploy/check-auth-cookie.sh) — запускать из корня установки на стенде, пароль он берёт из `backend/.env` и не печатает:

```bash
bash scripts/deploy/check-auth-cookie.sh
```

Проверено на DEV 10.08.2026, все пункты сошлись:

| --- | --- | --- |
| Токена нет в теле ответа на вход | нет | нет, `token_type: Cookie` |
| `cp_session` помечена `HttpOnly` | да | да |
| `cp_csrf` доступна из JavaScript | да | да, она и нужна фронтенду |
| Чтение по cookie и после обновления страницы | 200 | 200 |
| Изменение без признака CSRF | 419 | 419 |
| Изменение с чужим признаком | 419 | 419 |
| Истёкший токен | 401 | 401 |
| Выход с верным признаком | 200 | 200 |

Отдельно проверен мобильный контур на уровне запросов:

| Что | Результат |

Автоматические тесты: `CookieSessionTest` — тринадцать случаев, включая недоступность токена из JavaScript, отказ без признака и с чужим признаком, истёкший токен, вход, выход, продление и сеансовость cookie при снятой галочке.

| Галочка стоит: `cp_session` | со сроком | со сроком, 12 часов |

## Что должен посмотреть человек

Запросами нельзя проверить поведение интерфейса и камеру телефона. Это остаётся за владельцем.

**Адрес стенда:** `https://192.168.34.114:5443` изнутри сети, `https://84.54.208.134:5443` снаружи. Учётные записи — в [TEST_USERS.md](TEST_USERS.md), пароль общий.

**Важно:** все, кто был залогинен на DEV до выкатки, разлогинены. Это ожидаемо — надо войти заново.

### На компьютере

1. Войти под любой учётной записью. **Галочку «не выходить из сайта на этом устройстве» снять.** Портал должен открыться.
2. Нажать F12, вкладка Console, выполнить:
   ```js
   localStorage.getItem('college_portal_token')   // ожидается null
   sessionStorage.getItem('college_portal_token') // ожидается null
   document.cookie                                // cp_session здесь быть НЕ должно
   ```
   В `document.cookie` видны `cp_csrf` и `cp_persist` — так и задумано, секрета они не несут. Отсутствие `cp_session` в этом списке и есть то, ради чего задача делалась.
3. Обновить страницу (F5) — портал остаётся открытым, повторный вход не требуется.
4. Что-нибудь сохранить: например, открыть «Люди», выбрать человека, «Изменить данные», сохранить. Должно сохраниться без ошибок — это изменяющий запрос, и он идёт с признаком CSRF.
5. Закрыть браузер целиком и открыть заново на том же адресе. Так как галочка была снята, портал должен спросить вход.
6. Войти снова, **теперь галочку поставить**, закрыть и открыть браузер — портал должен остаться открытым.
7. Выйти через меню. Портал возвращает на форму входа, и кнопка «назад» в браузере не должна вернуть внутрь.

### На телефоне

Обе страницы требуют защищённого соединения, поэтому только по `https`.

8. Открыть `https://84.54.208.134:5443` (или адрес внутри сети), войти.
9. Открыть «Проходная» → «Сканер» (`/access/mobile-scanner`). Разрешить доступ к камере. Камера должна включиться, а наведение на QR — давать ответ о результате прохода. **Это главный пункт: сканер ходит тем же входом, и именно он мог пострадать от смены схемы.**
10. Открыть свой цифровой пропуск (`/identity/digital-passes`, строка пропуска, кнопка показа QR). Код должен отобразиться. На стенде для этого выпущен пропуск сотрудника — он там уже есть.

## Проверка пройдена владельцем 10.08.2026

Все шаги, включая телефон и сканер, владелец прошёл. **Блокер релиза снят.** Замечаний осталось три, и они разведены по областям: проверка ИНН и СНИЛС в карточке, политика выдаваемых паролей и поведение Firefox — разбор последнего ниже.

## Firefox не разлогинивает при снятой галочке

**Что видел владелец.** Firefox 153: вход со снятой галочкой «не выходить из сайта на этом устройстве», закрытие браузера, повторный запуск — портал открыт, вход не спрашивается. Chrome на том же стенде ведёт себя правильно и спрашивает вход.

**Что делает сервер.** Разобрано до правки чего-либо, потому что срок жизни, выставленный ради одного браузера, ослабил бы сеансовость во всех остальных.

Сеансовая cookie — это **отсутствие срока**, а не короткий срок: браузер обязан удалить её сам при закрытии. `SessionCookie::issue` при снятой галочке ставит `expires = 0` всем трём cookie, а скользящее продление для такой сессии cookie не переставляет вовсе — переставленная получила бы срок и пережила бы закрытие.

Проверено тремя способами, все сошлись:

- **живой стенд**, заголовки ответа на вход при `staySignedIn: false` — ни `Expires`, ни `Max-Age` ни у `cp_session`, ни у `cp_csrf`, ни у `cp_persist`; при `staySignedIn: true` у всех трёх появляется срок 12 часов;
- **тесты** `CookieSessionTest` — четыре новых случая: сеансовый вход, постоянный вход, продление сеансовой сессии не даёт cookie срока, продление постоянной срок сдвигает;
- **скрипт** `check-auth-cookie.sh` — те же три проверки машинно, чтобы это же можно было проверить на PROD после установщика.

**Вывод: сервер отдаёт настоящую сеансовую cookie.** Дальше решает браузер, и отличить восстановленную сеансовую cookie от продолжающейся сессии сервер не может в принципе — приходит она одинаково.

**Штатное поведение Firefox.** При включённой настройке «Открывать предыдущие окна и вкладки» Firefox восстанавливает вместе с сеансом и сеансовые cookie. С его точки зрения браузер не закрывался, а был свёрнут до следующего запуска. Chrome так не делает, поэтому разница между браузерами и видна.

### Два шага, которые подтвердят это окончательно

Оба делаются в Firefox и занимают минуту. **Их может сделать только человек** — из скрипта поведение перезапуска браузера не воспроизводится.

1. **Выключить восстановление сеанса:** «Настройки» → «Основные» → «Запуск» → снять «Открывать предыдущие окна и вкладки». Затем войти со снятой галочкой, закрыть браузер целиком, открыть заново. **Ожидается: портал спрашивает вход.**
2. **Приватное окно:** войти со снятой галочкой в приватном окне, закрыть **все** приватные окна, открыть новое. **Ожидается: портал спрашивает вход.** Приватные окна не восстанавливаются никогда, поэтому этот шаг отвечает и в том случае, если первую настройку менять не хочется.

**Если оба шага дают вход заново — дефекта у нас нет**, и запись выше описывает поведение браузера, а не портала.

**Если хотя бы один шаг снова открывает портал авторизованным — дефект наш**, сообщите, и разбор продолжится: следующее место, куда смотреть, — не подставляет ли что-то на странице признак постоянства, то есть не приходит ли `cp_persist=1` там, где галочка снята.

### Что можно сделать со стороны портала, если поведение Firefox не устраивает

Это **не сделано**: решение за владельцем, потому что меняет поведение для всех.

Сегодня скользящее продление сдвигает срок жизни токена в базе **и при снятой галочке** — cookie при этом не переставляется, но сама сессия остаётся действующей, пока человек работает. То есть если Firefox вернул cookie, сессия продолжится.

Можно сделать так, чтобы сессия со снятой галочкой **не продлевалась вовсе**: тогда она умрёт не позже чем через 12 часов после входа, чем бы браузер её ни восстановил. Цена — человек, работающий со снятой галочкой больше 12 часов подряд, будет выкинут посреди работы. Скажите, если такой размен нужен.

## На PROD не разворачивалось

Выкатка разлогинит всех, кто там работает. Отдельное поручение обязательно. Порядок обычный: собрать релиз на DEV, обновить PROD установщиком, сразу после обновления прогнать `scripts/deploy/check-auth-cookie.sh` на боевом адресе и войти в браузере под одной учётной записью, прежде чем расходиться.
