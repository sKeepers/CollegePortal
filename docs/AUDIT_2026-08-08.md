#### 1. Пятеро с одного адреса блокируют вход всем остальным, а подбор пароля по учётной записи не ограничен ничем

**Дефект.** Ограничитель попыток входа считает по паре «IP + email», но форма входа поле `email` не отправляет никогда — она отправляет `login`, поэтому ключ схлопывается до одного только IP-адреса.

**Где.**
- [backend/app/Providers/AppServiceProvider.php:37-41](../backend/app/Providers/AppServiceProvider.php#L37-L41) — `$email = Str::lower((string) $request->input('email'));` и `Limit::perMinute(5)->by($request->ip().'|'.$email)`
- [backend/app/Http/Requests/LoginRequest.php:18-19](../backend/app/Http/Requests/LoginRequest.php#L18-L19) — принимаются оба поля, `login` и `email`
- [frontend/src/pages/auth/LoginPage.vue:11](../frontend/src/pages/auth/LoginPage.vue#L11) и [:18](../frontend/src/pages/auth/LoginPage.vue#L18) — форма шлёт `{ login, password }`, поля `email` в ней нет

**Как проявляется у пользователя.** Два разных сценария из одной причины.

*Первый.* Утро, кабинет за общим шлюзом или общий Wi-Fi. Пять человек подряд ошиблись паролем (для пятизначного пароля, который выдаёт портал, это обычное дело). Шестой вводит **правильный** пароль и получает «Слишком много попыток». Он ничего не сделал не так, ошибиться не мог, а войти не может минуту. На DEV ситуация ещё жёстче: перед nginx там стоит https-прокси, а `TrustProxies` не настроен, поэтому все запросы, пришедшие через HTTPS-вход (а это оба документированных адреса DEV), видятся с одного адреса контейнера `172.18.0.4` — то есть пять неверных попыток любого пользователя блокируют вход **всем остальным пользователям DEV** (это же подтверждает находка 11).

*Второй.* Защиты от подбора пароля конкретного человека нет вообще. Логин генерируется предсказуемо — `ivanov.ds` или номер телефона в форме `+7XXXXXXXXXX`, — а пароль это `random_int(10000, 99999)`, всего 90 000 вариантов. Пять попыток в минуту с адреса, но адресов у атакующего может быть много, и ни один счётчик не привязан к самой учётной записи.

**Почему так вышло.** Ограничитель писали, когда вход был по email. Потом вход переделали на универсальный `login` (email, username или телефон в любой записи) — и не заметили, что ключ ограничителя остался от старой формы. Ровно тот же шов «две половины делали отдельно»: `LoginRequest` про новую половину знает, `RateLimiter` — нет.

**Серьёзность.** Блокирует работу. Плюс существенно ослабляет защиту перед загрузкой реальных персональных данных.

**Что предлагается.** Ключ ограничителя строить по тому же значению, которое контроллер использует для поиска пользователя: `$request->input('login') ?: $request->input('email')`, нормализованному так же, как в `AuthController::login`. И завести **два** ограничителя: по учётной записи (жёсткий, с прогрессивной задержкой) и по адресу (мягкий, чтобы общий NAT не ронял всех). Именно два, а не один: они защищают от разного, и любой одиночный ключ обязательно пожертвует либо защитой от подбора, либо работоспособностью за общим адресом. Отдельно и независимо — политика пароля: пять цифр не выдерживают контура с ПДн, но это решение владельца, оно уже стоит в `ACTIVE_WORK`.

#### 2. Двенадцать пар «роль — экран»: пункт меню виден, а страница не открывается

**Дефект.** Страница грузит справочники одним `Promise.all`, и если хотя бы на один справочник у роли нет права, отклоняется весь `Promise.all` — экран не показывает ничего.

**Где.**
- [frontend/src/layouts/AppLayout.vue:70-138](../frontend/src/layouts/AppLayout.vue#L70-L138) — пункт меню показывается по **одному** праву
- [frontend/src/stores/groups.js:102-106](../frontend/src/stores/groups.js#L102-L106), [stores/curricula.js:88-90](../frontend/src/stores/curricula.js#L88-L90), [stores/graduation.js:38](../frontend/src/stores/graduation.js#L38), [stores/exams.js:83-85](../frontend/src/stores/exams.js#L83-L85), [stores/teachers.js:118-122](../frontend/src/stores/teachers.js#L118-L122), [stores/frdo.js:33](../frontend/src/stores/frdo.js#L33), [stores/digitalPasses.js:55-60](../frontend/src/stores/digitalPasses.js#L55-L60), [stores/attendanceAnalysis.js:113-116](../frontend/src/stores/attendanceAnalysis.js#L113-L116) — страница требует прав больше, чем меню
- [backend/app/Http/Middleware/EnsurePermission.php:100-146](../backend/app/Http/Middleware/EnsurePermission.php#L100-L146) — таблица, по которой считается требуемое право
- [backend/database/seeders/RoleSeeder.php:237-273](../backend/database/seeders/RoleSeeder.php#L237-L273) — наборы прав `study` и `study_records`

**Как проявляется у пользователя.** Подтверждено тестом, ходящим по HTTP от имени каждой роли:

| --- | --- | --- |
| `study_records` | Группы | `education-programs` |
| `study_records` | Учебные планы | `education-programs`, `specialties`, `admin/reference/items` |
| `study_records` | Выпускники и дипломы | `education-programs`, `specialties` |
| `study_records` | ФРДО | `education-programs` |
| `admission` | Группы | `teachers` |
| `teacher` | Экзамены и ГИА | `groups`, `subjects`, `teachers`, `classrooms`, `students` |

| `curator` | Посещаемость | `teachers` |

Конкретно: методист «Учебной части 2» — та самая роль, которую завели под контингент и выпуск, — открывает «Группы» и видит «Не удалось загрузить группы». Открывает «Выпускники и дипломы» — «Не удалось загрузить выпускников». Открывает «Учебные планы» — то же. Четыре из шести доступных ей разделов не работают. Преподаватель открывает «Экзамены и ГИА» и не видит ничего. На «Посещаемости» хуже: там `loadOptions()` не обёрнут в `try/catch` ([AttendancePage.vue:153-157](../frontend/src/pages/attendance/AttendancePage.vue#L153-L157)), отказ промиса никто не ловит, следующая строка `await store.load()` не выполняется — экран остаётся пустым **без всякого сообщения**.

**Почему так вышло.** Право на показ пункта меню и права, нужные странице, назначались в разных местах и в разное время: меню — во фронтенде по одному «главному» праву, справочники — в сторе по мере того, как страница обрастала выпадающими списками, права ролей — в сидере. Никто не сверял три списка между собой. Разделение `academic_office` на `study` и `study_records` в rc6 добавило две роли с новыми наборами прав, и на них это вылезло сразу.

**Серьёзность.** Блокирует работу. Роль `study_records` в нынешнем виде нерабочая.

**Что предлагается.** Две меры, обе нужны.

Во-первых, **право видеть пункт меню должно вычисляться из того, что странице действительно нужно**, а не задаваться отдельной строкой. Иначе списки снова разойдутся при следующем изменении. Практически: рядом с каждым разделом объявить набор его запросов, показывать пункт по этому набору, а не по одному праву.

Во-вторых, **справочники грузить устойчиво**: `Promise.allSettled` вместо `Promise.all`, как уже сделано в `stores/schedule.js:220`. Отсутствие права на справочник обязано означать «выпадающий список пуст», а не «страница не открылась». Правильный образец в проекте уже есть — [JournalPage.vue:199-200](../frontend/src/pages/journal/JournalPage.vue#L199-L200) спрашивает `hasPermission('journal.reopen')` перед запросом, а [TeachingLoadPage.vue:122](../frontend/src/pages/teaching-load/TeachingLoadPage.vue#L122) передаёт `includeReferenceData: false` для роли без прав на справочники. Осталось применить это ко всем остальным.

И отдельно — решить по существу: должна ли `study_records` видеть образовательные программы и специальности. Похоже, что должна (она ведёт группы и выпуск), и тогда достаточно добавить ей `reference.manage` на чтение. Но лечить только сидером нельзя: механизм останется хрупким.

#### 3. Импорт учебных планов, нагрузки, экзаменов и выпускников не снимает BOM — и создаёт дубликаты вместо обновления

**Дефект.** Четыре импорта читают заголовок через `fgetcsv` и подставляют его в `array_combine` как есть. Байт-маркер порядка (BOM), который Excel ставит при сохранении в «CSV UTF-8», приклеивается к первой колонке — а первая колонка это `id`, по которому импорт отличает обновление от создания.

**Где.**
- [backend/app/Http/Controllers/Api/CurriculumController.php:199](../backend/app/Http/Controllers/Api/CurriculumController.php#L199) и [:232](../backend/app/Http/Controllers/Api/CurriculumController.php#L232) — `$headers = fgetcsv($handle, 0, ';')`, затем `!empty($data['id']) ? Curriculum::find(...) : null`
- [backend/app/Http/Controllers/Api/TeachingLoadController.php:198](../backend/app/Http/Controllers/Api/TeachingLoadController.php#L198) и [:233](../backend/app/Http/Controllers/Api/TeachingLoadController.php#L233)
- [backend/app/Http/Controllers/Api/ExamController.php:145](../backend/app/Http/Controllers/Api/ExamController.php#L145) и [:199](../backend/app/Http/Controllers/Api/ExamController.php#L199)
- [backend/app/Http/Controllers/Api/GraduateController.php:132](../backend/app/Http/Controllers/Api/GraduateController.php#L132) — то же чтение заголовка; здесь запись ищется по `student_id`, а не по `id`, поэтому дубликатов не даёт, но колонка теряется так же

**Как проявляется у пользователя.** Замер на тестовых данных:

```
Нагрузок:                       было 1, после чистого импорта 1, после импорта с BOM 3
Экзаменов:                      было 1, после чистого импорта 1, после импорта с BOM 2
Учебных планов (без кода):      было 1, после чистого импорта 1, после импорта с BOM 3
```

Сценарий целиком: методист выгружает нагрузку, открывает файл в Excel, правит часы, сохраняет, загружает обратно. Портал отвечает «Импорт завершён» и **создаёт новую нагрузку на каждую строку файла**. У нагрузки из тридцати строк вместо одной исправленной записи появляется тридцать одна. Ошибок не показано, потому что с точки зрения импорта это обычное создание.

У учебных планов **с** заполненным кодом вместо дубликатов срабатывает уникальный индекс, и пользователь получает вот такое:

```
SQLSTATE[23000]: Integrity constraint violation: 19 UNIQUE constraint failed: curricula.code
```

То есть импорт целиком ничего не делает и показывает текст ошибки базы данных. Это не лучше — просто ломается иначе.

**Почему так вышло.** BOM в этом проекте уже ловили: в rc7 его починили в `UniversalImportService` ([:184](../backend/app/Services/UniversalImportService.php#L184) и [:212](../backend/app/Services/UniversalImportService.php#L212)) и во всех восьми `*CsvService` (`trim($header, "\xEF\xBB\xBF ...")`). Но у учебных планов, нагрузки, экзаменов и выпускников импорт написан прямо в контроллере, отдельным куском кода, и до него исправление не дошло. Одна и та же задача решена в трёх местах из четырёх.

**Серьёзность.** Портит данные. Молча, при обычной работе, без единого сообщения об ошибке.

**Что предлагается.** Не приклеивать пятое исправление BOM к четырём контроллерам, а убрать эти четыре самописных импорта и перевести учебные планы, нагрузку и экзамены на `UniversalImportService` — там уже есть и снятие BOM, и распознавание разделителя, и сопоставление колонок по синонимам, и поток «предпросмотр → проверка → подтверждение», и обработчики `CurriculumImportHandler`, `TeachingLoadImportHandler` для этих же типов **уже написаны и покрыты тестами** (`UniversalImportApiTest`: «it imports curricula rows through universal import», «it imports teaching load rows through universal import»). Сейчас в портале два независимых импорта одних и тех же сущностей, и починен только один. Пока перевод не сделан — как временная мера снять BOM в четырёх местах.

#### 4. Половина выгрузок пишет BOM, половина нет: файл открывается в Excel кракозябрами

**Дефект.** Из тринадцати проверенных выгрузок девять начинают файл с BOM, четыре — нет. Excel без BOM читает UTF-8 как ANSI.

**Где.** Подтверждено прогоном по всем выгрузкам:

```
С BOM:   students/export, teachers/export, groups/export, subjects/export,
         classrooms/export, specialties/export, education-programs/export,
         employees/export, applicant-applications/export
БЕЗ BOM: curricula/export, exams/export, graduates/export, teaching-loads/export
```

К четырём без BOM добавляются те, что в тест не попали, но написаны так же: [AccessReportController.php:169](../backend/app/Http/Controllers/Api/AccessReportController.php#L169) (отчёт проходной, заголовки русские), выгрузки журнала в `JournalLessonController`, выгрузки UAT, `DemoDataController::export`, `StudentBulkService::export`.

**Как проявляется у пользователя.** Заведующий отделением выгружает нагрузку и открывает двойным щелчком. Вместо «Петрова Анна Викторовна» и «Аудиторная» — `Ïåòðîâà Àííà`. Файл выглядит испорченным. Дальше человек либо бросает эту затею, либо пересохраняет файл «правильно» — и попадает в находку 3.

**Почему так вышло.** BOM добавляли по мере того, как на конкретную выгрузку жаловались. Общего места, где формируется CSV, нет: каждая выгрузка сама открывает `php://output` и сама решает, писать маркер или нет.

**Серьёзность.** Мешает. Сама по себе — только неудобство, но в связке с находкой 3 образует полный путь к порче данных: кракозябры → пересохранение в Excel → дубликаты.

**Что предлагается.** Один хелпер, отдающий CSV: BOM, разделитель `;`, `Content-Type`. Все выгрузки — через него. Это же снимает вопрос о разделителе: сейчас все пишут `;` вручную, и однажды кто-нибудь напишет запятую.

- [:27-41](../backend/app/Http/Controllers/Api/AccessReportController.php#L27-L41) — `summary()` считает `entries`, `exits`, `denied` по этой же выборке
- [:123-127](../backend/app/Http/Controllers/Api/AccessReportController.php#L123-L127) — `only_late` фильтрует **после** обрезания
- [:63-73](../backend/app/Http/Controllers/Api/AccessReportController.php#L63-L73) — экспорт получает те же обрезанные события

**Как проявляется у пользователя.** Замер: при 1200 событиях в базе за период сводка показывает 1000 входов, в выгрузке 1000 строк. Колледж на 500 человек даёт больше тысячи проходов за два-три дня. Значит, отчёт за месяц — это отчёт за последние два дня, и он не подписан как таковой. Хуже всего с «только опоздавшими»: опоздания ищутся в последней тысяче событий, поэтому опоздавший в начале месяца в отчёт не попадёт никогда. Проверка табельной дисциплины по такому отчёту даёт неверный ответ, причём уверенно.

**Почему так вышло.** `limit(1000)` — разумная защита списка на экране (там дополнительно `take(200)`). Потом на тот же метод повесили сводку, фильтр опозданий и выгрузку, а ограничение осталось внизу, где его не видно.

**Серьёзность. Портит данные** в том смысле, что отчёт, по которому принимают кадровые решения, систематически неполон и об этом не сообщает.

**Что предлагается.** Сводные счётчики считать запросом-агрегатом в базе, без выборки строк. Фильтры «только опоздавшие» и поиск перенести в SQL, до ограничения. Для выгрузки ограничение снять и стримить курсором — выгрузку затем и заказывают, что она полная. Ограничение оставить только на списке для экрана и подписать его в интерфейсе: «показаны последние 200 из N».

**Как проявляется у пользователя.** Кадровик выгружает сотрудников «чтобы был файл» — например, перед очисткой рабочих данных, как прямо предписано в [ACTIVE_WORK.md:51](ACTIVE_WORK.md#L51). **Серьёзность.** Мешает; при выгрузке перед очисткой — теряет данные.

**Что предлагается.** Добавить «Дата рождения» и «СНИЛС» в `templateHeaders()` сотрудников: обработчик их и так принимает, необязательными они и останутся, а импорт совместимость не потеряет — колонки сопоставляются по синонимам, не по позиции. Заодно закрывается пункт 3 «Следующих действий» в `ACTIVE_WORK`.

#### 11. Журнал аудита записывает адрес прокси вместо адреса пользователя

**Дефект.** `TrustProxies` не настроен, поэтому за обратным прокси `$request->ip()` возвращает адрес прокси.

**Где.**
- [backend/bootstrap/app.php:17-22](../backend/bootstrap/app.php#L17-L22) — в `withMiddleware()` только алиасы, вызова `trustProxies()` нет; во всём `backend/` нет ни одного упоминания `TrustProxies` или `X-Forwarded`
- [backend/app/Services/AuditLogService.php:50](../backend/app/Services/AuditLogService.php#L50) — `'ip_address' => $request?->ip()`
- [infra/dev-https/nginx-https.conf:16-21](../infra/dev-https/nginx-https.conf#L16-L21) — DEV-прокси ставит `X-Forwarded-For`, но его никто не читает

**Как проявляется у пользователя.** На DEV прямо сейчас:

```
 ip_address    | count
 172.18.0.4    |    74
 192.168.34.16 |    16
```

74 записи из 90 указывают на внутренний адрес контейнера. Расследовать «кто и откуда это сделал» по такому журналу нельзя.

**Оговорка, важная для оценки серьёзности.** На PROD релизный nginx ходит в backend через `fastcgi_pass`, а `fastcgi_params` передаёт `REMOTE_ADDR = $remote_addr` — то есть **на PROD в аудит попадает настоящий адрес клиента**, пока перед nginx нет ещё одного прокси. Проблема сегодня живая на DEV и станет живой на PROD в день, когда портал спрячут за CDN, балансировщик или корпоративный прокси. Это же ухудшает находку 1: за прокси все попытки входа считаются как с одного адреса.

**Серьёзность.** На DEV — мешает (журнал аудита бесполезен). На PROD — отложенный риск.

**Что предлагается.** Настроить `trustProxies()` явно, с перечнем адресов, а не `'*'`: доверять заголовку от кого попало — значит позволить подменять адрес в журнале аудита и обходить ограничитель входа.

- **Пароли и токены.** Пароль хранится только хешем (`'password' => 'hashed'` в [User.php:60](../backend/app/Models/User.php#L60)), из журнала аудита вычищается [AuditLogService.php:70-83](../backend/app/Services/AuditLogService.php#L70-L83), в массовой выдаче ветка `credentials` снимается перед записью в аудит [StudentBulkService.php:59-62](../backend/app/Services/Bulk/StudentBulkService.php#L59-L62), в ответ уходит один раз и нигде не сохраняется. Отдельно чистятся СНИЛС, серии и номера документов, адреса, телефоны. Это сделано аккуратно.
- **События компонентов.** Все `@apply`/`@reset`/`@update:model-value` на компонентах фронтенда сверены с их `defineEmits` — расхождений нет. Дефект `AppFilterBar` из rc7 закрыт правильно: страницы больше не слушают несуществующие события, у фильтров есть собственные компоненты со своими `emits`.

## 3. Заключение

**Где система крепка.** Ядро сделано добротно. Права хранятся как данные, а не как код. Пароли и персональные данные вычищаются из журнала аудита продуманно — там видна работа, а не формальность. Сервисный слой на месте, бизнес-правила, вокруг которых уже обжигались, сведены в единственное место и закреплены тестами. 407 тестов зелены и на SQLite, и на PostgreSQL 17. Универсальный импорт — сильная вещь: снятие BOM, синонимы колонок, предпросмотр с проверкой до применения. Движок расписания проверяет конфликты в обе стороны, включая legacy-таблицу.

**Где тонко.** Две причины дают почти все находки, и обе — про швы.

**Первая: одна и та же задача решена в нескольких местах, и чинят по одному.** Импорт CSV написан трижды — в `UniversalImportService`, в восьми `*CsvService` и прямо в четырёх контроллерах. BOM починили в первых двух, до третьего не дошли (находка 3). Формирование CSV на выгрузку написано в тринадцати местах, BOM пишут девять (находка 4). Импорт учебных планов и нагрузки существует в двух экземплярах одновременно, причём для универсального обработчики написаны и покрыты тестами, а работает в интерфейсе самописный. Пока задача решается в нескольких местах, каждое исправление закрывает ровно одно из них, и следующий аудит найдёт остальные.

**Вторая: право доступа выводится из трёх независимых списков, которые никто не сверяет.** Право на пункт меню лежит во фронтенде, право на маршрут выводится из префикса URL по таблице в middleware, набор прав роли — в сидере. Совпадать они не обязаны, и не совпадают: двенадцать пар «роль — экран» (находка 2), 21 маршрут вне таблицы (находка 8). Возврат `reference.manage` по умолчанию превращает промах в тихую выдачу чужого права вместо явной ошибки. Сегодня спасает то, что ролям щедро роздано legacy-право `manage_dictionaries`; в тот день, когда администратор наведёт порядок в матрице разрешений, отвалится сразу многое.

**Что поменять, чтобы не возвращаться.** Не заплатки, а два изменения.

1. **Один вход для CSV в обе стороны.** Весь импорт — через `UniversalImportService`, вся выгрузка — через общий хелпер. Тогда BOM, разделитель, кавычки и кодировка чинятся однажды и навсегда, а не тринадцать раз.
2. **Список запросов раздела как единственный источник правды о правах.** Пункт меню показывать по нему, доступ проверять по нему, тест, обходящий все роли и все разделы, гонять в CI. Такой тест написан в рамках этого аудита (приложен ниже) — его достаточно внести в набор, и следующие двенадцать расхождений найдёт CI, а не пользователь.

namespace Tests\Feature;

use App\Models\AccessEvent;
use App\Models\DigitalIdentity;
use Illuminate\Foundation\Testing\RefreshDatabase;
use Tests\TestCase;

/**
 * Отчёт проходной берёт только 1000 последних событий, и уже по этой
 * обрезанной выборке считает сводку, фильтрует «только опоздавших»
 * и формирует выгрузку.
 */
class AuditAccessReportLimitTest extends TestCase
{
    use RefreshDatabase;

    public function test_summary_and_export_are_silently_capped_at_one_thousand_events(): void
    {
        $this->withApiAuth();

        $rows = [];
        $start = now()->startOfMonth();
        for ($i = 0; $i < 1200; $i++) {
            $rows[] = [
                'digital_identity_id' => null,
                'access_point_id' => null,
                'entity_type' => DigitalIdentity::ENTITY_STUDENT,
                'entity_id' => 1,
                'direction' => AccessEvent::DIRECTION_IN,
                'event_time' => $start->copy()->addMinutes($i),
                'access_point' => 'Турникет 1',
                'device_name' => 'dev',
                'result' => AccessEvent::RESULT_ALLOWED,
                'reason' => null,
                'created_at' => now(),
                'updated_at' => now(),
            ];
        }
        AccessEvent::insert($rows);

        $from = $start->copy()->subDay()->toDateString();
        $to = $start->copy()->addMonth()->toDateString();

        $entries = $this->getJson("/api/access/reports/summary?date_from={$from}&date_to={$to}")
            ->assertOk()->json('data.entries');

        $csv = $this->get("/api/access/reports/events?export=csv&date_from={$from}&date_to={$to}")->streamedContent();
        $lines = substr_count(rtrim($csv, "\n"), "\n"); // без строки заголовка

        $this->assertSame(1000, $entries, 'сводка не обрезана');
        $this->assertSame(1000, $lines, 'выгрузка не обрезана');
    }
}
