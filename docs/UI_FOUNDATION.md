# UI Foundation CollegePortal

Дата: 2026-06-29

Основание: ADR-001 (`docs/ARCHITECTURE_DECISIONS.md`) и концепция GUI (`docs/UI_CONCEPT.md`).

Стек UI:

- Quasar — основная UI-платформа;
- Tailwind CSS — слой кастомизации и фирменного стиля;
- Lucide Icons — основной набор иконок.

## Цвета

Базовая палитра:

- `primary`: `#2563eb` — основное действие, активная навигация, ссылки;
- `secondary`: `#475569` — вторичные действия и нейтральные подписи;
- `accent`: `#f59e0b` — фирменный акцент CollegePortal;
- `dark`: `#111827` — левое меню и темные рабочие элементы;
- `brand-dark`: `#0f172a` — темная основа интерфейса и PWA theme color;
- `brand-white`: `#ffffff` — фон официального черно-белого знака колледжа в favicon, PWA-иконках и sidebar;
- `background`: `#eef2f7` — фон рабочей области;
- `surface`: `#ffffff` — панели, карточки, формы;
- `border`: `#d9e2ef` / `#e2e8f0` — границы;
- `text`: `#172033` — основной текст;
- `muted`: `#64748b` — вторичный текст.

Смысловые цвета:

- успех: `#047857`, фон `#ecfdf5`;
- предупреждение: `#c2410c`, фон `#fff7ed`;
- ошибка: `#991b1b`, фон `#fff1f2`;
- информация: `#1d4ed8`, фон `#eff6ff`;
- архив/неактивно: `#64748b`, фон `#f1f5f9`.

## Типографика

Шрифт:

- системный стек `Inter, ui-sans-serif, system-ui, Segoe UI, sans-serif`;
- отрицательный letter-spacing не использовать;
- размер не масштабировать через viewport width.

Размеры:

- заголовок страницы: 20-24px;
- заголовок панели: 16-18px;
- основной текст: 14px;
- таблицы и вторичные данные: 12-13px;
- служебные подписи: 11-12px.

## Отступы

Базовая сетка:

- 4px — минимальный шаг;
- 8px — компактные промежутки;
- 12px — стандартный внутренний отступ компактных блоков;
- 16px — панели и карточки;
- 22-24px — рабочая область desktop.

## Плотность интерфейса

Интерфейс CollegePortal должен быть плотным, но читаемым:

- таблицы компактные;
- формы без лишних вертикальных промежутков;
- панели с радиусом 8px или меньше;
- не вкладывать карточки в карточки без необходимости;
- не использовать декоративные hero-блоки в рабочем интерфейсе.

## Брендинг

Фирменный знак CollegePortal использует официальный черно-белый логотип Ставропольского краевого колледжа искусств из `docs/logo/Logo_SKKI_чб.jpg`.

- `frontend/public/brand/logo-skki-bw.jpg` — копия официального черно-белого знака для frontend;
- `frontend/public/favicon.svg` — SVG-обертка с официальным знаком;
- `frontend/public/favicon.ico` — fallback для браузеров;
- `frontend/public/apple-touch-icon.png` — иконка для устройств Apple;
- `frontend/public/icons/icon-192.png` и `frontend/public/icons/icon-512.png` — PWA-иконки;
- sidebar использует официальный знак на белой компактной плашке, чтобы черный логотип был читаемым на темной панели.

Запрещено придумывать новые варианты логотипа, менять форму знака или добавлять цветные подложки. Допустимо только техническое масштабирование официального изображения под favicon/PWA-размеры с сохранением пропорций.

## Правила кнопок

Типы:

- primary — главное действие страницы;
- secondary/flat — вторичные действия;
- danger — удаление и необратимые действия;
- icon button — компактные действия в таблицах и toolbars.

Правила:

- текст кнопки должен быть глаголом: `Создать`, `Сохранить`, `Удалить`, `Экспорт`;
- опасные действия требуют подтверждения;
- loading/disabled состояния обязательны;
- иконка используется только если помогает распознаванию.

## Правила таблиц

Таблицы строятся на Quasar `QTable`.

Правила:

- заголовки короткие;
- действия в последней колонке;
- строковые действия делать компактными icon button;
- важные статусы — через `AppStatusBadge`;
- пустой список — через `AppEmptyState`;
- выбранная строка подсвечивается;
- ФИО или главный идентификатор записи может быть кликабельным для открытия карточки;
- для больших списков нужна серверная пагинация;
- фильтры не размещать внутри строк.
- подпись выбора размера страницы — `Записей на странице:`;
- варианты размера страницы для CRUD: `10`, `20`, `50`, `Все`;
- выбранный размер страницы сохранять через `frontend/src/services/tableSettings.js`.
- связанные сущности показывать как спокойные action-ссылки или action-chip, чтобы пользователь видел возможность перехода без перегруза яркими ссылками.
- на страницах “таблица + карточка” таблица должна оставаться в отдельной левой колонке и прокручиваться внутри своей области; карточка не должна перекрывать последние колонки таблицы. На узкой рабочей ширине карточка переносится под таблицу. Подробные правила описаны в `docs/LAYOUT_GUIDELINES.md`.

## Правила форм

Формы строятся на Quasar inputs и группируются через `AppFormSection`.

Правила:

- поля объединяются по смыслу;
- ошибки показываются рядом с полем;
- обязательные поля явно видны;
- длинные формы не помещать в маленькие модальные окна;
- действия формы держать внизу секции.

## Правила фильтров

Фильтры строятся через `AppFilterBar`.

Правила:

- расположение над таблицей;
- частые фильтры видны сразу;
- редкие фильтры допускается убирать в раскрытие;
- активные фильтры отображать чипами;
- чипы активных фильтров должны сниматься без перезагрузки страницы;
- должен быть быстрый сброс;
- применение фильтров не должно ломать состояние страницы.

## Правила карточек

Карточки строятся через `AppCard`.

Правила:

- карточка показывает подробности выбранной записи;
- заголовок + статус + действия;
- для сложной карточки использовать вкладки;
- шапка карточки должна сразу показывать имя/название, статус и ключевой контекст;
- быстрые показатели размещать до вкладок;
- данные разбиваются на секции;
- карточка не должна заменять таблицу;
- карточка должна помогать быстро понять состояние записи.

## Правила статусов

Статусы строятся через `AppStatusBadge`.

Правила:

- цвет + текст, не только цвет;
- зеленый — готово/активно;
- оранжевый — требует внимания;
- красный — ошибка/отклонено;
- серый — архив/неактивно;
- синий — информационное состояние.

## Правила модальных окон

Модальные окна использовать для:

- подтверждения удаления;
- коротких действий;
- небольших справок;
- выбора одного параметра.

Не использовать для:

- больших форм;
- длинных таблиц;
- карточки студента или заявления.

## Правила уведомлений

Уведомления:

- успешное действие: короткое toast-сообщение;
- ошибка API: `AppErrorBanner` или toast, если ошибка контекстная;
- предупреждение: явно указать, что нужно исправить;
- загрузка: `AppLoading`, не сдвигающий layout.

## Шаблон обычной CRUD-страницы

Структура:

1. `AppPage`
2. `PageHeader`
3. `AppToolbar`
4. `AppFilterBar`
5. `AppErrorBanner`
6. `AppTable`
7. `AppEmptyState`, если данных нет
8. `AppCard` или detail panel для выбранной записи
9. `AppConfirmDialog` для удаления

Минимальные действия:

- создать;
- редактировать;
- удалить;
- импортировать, если поддерживается;
- экспортировать, если поддерживается.

Первые эталоны применения шаблона — разделы `frontend/src/pages/students/StudentsPage.vue`
и `frontend/src/pages/groups/GroupsPage.vue`. Разделы «Преподаватели» и «Дисциплины» следуют тому же шаблону через `frontend/src/pages/teachers/TeachersPage.vue` и `frontend/src/pages/subjects/SubjectsPage.vue`.
Новые CRUD-разделы следует переносить по этой структуре: store Pinia для API и состояния,
отдельный компонент фильтров, отдельная форма, карточка выбранной записи и `AppConfirmDialog`
для удаления. Эталон GUI-003.2 также включает активные фильтры-чипы, уведомления Quasar Notify,
выделение выбранной строки, компактные действия в таблице, вкладки в detail panel,
русскую пагинацию и сохранение выбранного размера страницы.
Связи между модулями следует делать через Vue Router query-параметры, если это не требует изменения API:
например `/students?group=<id>` и `/groups?selected=<id>`.

## Шаблон Dashboard-страницы

Dashboard строится как набор рабочих виджетов:

1. `AppPage`
2. `PageHeader`
3. приветственный блок с датой и именем пользователя
4. `StatsWidget` во всю ширину
5. сетка рабочих виджетов в 2 колонки на desktop
6. одна колонка на узких экранах

Правила:

- виджеты должны быть компактными;
- данные загружаются на уровне `DashboardPage.vue` или будущего dashboard-store;
- mock-данные явно отделяются в коде префиксом `mock`;
- виджеты не должны содержать сложную бизнес-логику;
- быстрые действия ведут в существующие разделы и не создают скрытых side effect.

## Шаблон страницы расписания

Расписание не должно выглядеть как обычный CRUD-справочник. Для него используется рабочая доска:

1. `AppPage`
2. `PageHeader`
3. переключатель представлений: `День`, `Неделя`, `Преподаватель`, `Группа`, `Аудитория`
4. управление периодом
5. `AppFilterBar` с учебным годом, семестром, группой, преподавателем, аудиторией и дисциплиной
6. `AppToolbar` с текущим периодом, загрузкой и обновлением
7. сводные показатели
8. левая область с карточками занятий
9. правая карточка выбранного занятия

Правила:

- представление `Неделя` используется по умолчанию;
- занятие выделяется цветом по типу занятия;
- карточка занятия справа должна показывать дисциплину, преподавателя, группу, аудиторию, дату, время и тип;
- связанные действия открывают журнал, группу, преподавателя и аудиторию;
- layout следует `docs/LAYOUT_GUIDELINES.md`: карточка справа не перекрывает расписание, на узкой ширине переносится ниже.

## Шаблон страницы отчета

Структура:

1. `AppPage`
2. `PageHeader`
3. `AppFilterBar` с параметрами отчета
4. `AppToolbar` с `Сформировать` и `Экспорт`
5. `AppCard` со сводкой
6. `AppTable` с результатами
7. `AppEmptyState`, если отчет пуст
8. `AppErrorBanner`, если отчет не сформирован из-за ошибки

Правило: табличный результат важнее графика. Графики добавлять только если они помогают принять решение.
