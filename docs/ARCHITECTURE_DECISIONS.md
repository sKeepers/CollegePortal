# Architecture Decisions

Этот файл фиксирует ключевые архитектурные решения проекта CollegePortal.

## ADR-001: выбор frontend UI-платформы для CollegePortal

Дата: 2026-06-29

Статус: принято.

Реализация: первый практический этап начат 2026-06-29. Quasar подключен к текущему Vue/Vite frontend без создания нового проекта. Старый `frontend/src/App.vue` сохранен как legacy до полной миграции разделов. Этап GUI-002 добавил UI Foundation и демонстрационную страницу `/system/ui-foundation` для администратора.

### Контекст

CollegePortal начинает этап переработки GUI. Нужно доработать текущий frontend поверх существующего Laravel API, не создавая новый проект, не меняя backend и не меняя базу данных.

Проект некоммерческий, поэтому для основной frontend-платформы нужны бесплатные лицензии без риска будущей обязательной коммерческой оплаты.

Интерфейс должен поддерживать:

- desktop-интерфейс сотрудников колледжа;
- большое количество таблиц и форм;
- журнал;
- расписание;
- отчеты;
- карточки студентов;
- приемную комиссию;
- будущий мобильный кабинет студента;
- будущие сценарии для преподавателей;
- будущие интеграции с Moodle, ФРДО и ФИС ГИА/Приема.

Рассматривались:

- PrimeVue;
- Vuetify;
- Quasar.

Дополнительно рассматривались:

- Tailwind CSS;
- PrimeFlex;
- Tabler Icons;
- Lucide Icons;
- Heroicons.

Подробное исследование: `docs/research/ui-framework-comparison.md`.

### Решение

Использовать для нового GUI:

**Quasar + Tailwind CSS + Lucide Icons**

### Причины

- проект некоммерческий;
- нужны только бесплатные лицензии;
- Quasar имеет MIT-лицензию;
- Quasar подходит для desktop-интерфейса сотрудников;
- Quasar подходит для будущего мобильного кабинета студента;
- Quasar дает готовые layout/drawer/page/table/dialog/upload/menu/dark-mode/responsive patterns;
- Quasar совместим с Vue 3, Vite и Pinia;
- Quasar можно использовать поверх существующего Laravel REST API без переписывания backend;
- Tailwind CSS использовать для кастомизации, плотного рабочего интерфейса и фирменного стиля CollegePortal;
- Lucide Icons использовать как основной набор иконок: легкий, единый по стилю, tree-shakable, с подходящей лицензией.

### Почему не PrimeVue

PrimeVue функционально очень силен для таблиц, форм, TreeTable и учетных интерфейсов. Однако на дату принятия решения есть лицензионный риск для будущих major-версий PrimeVue/PrimeUI.

Для CollegePortal нежелательно создавать зависимость от UI-платформы, которая в будущем может потребовать коммерческого лицензирования или отдельного юридического согласования.

### Почему не Vuetify

Vuetify остается надежным MIT-вариантом, но Quasar лучше закрывает будущий мобильный/PWA-сценарий и дает более цельную платформу для desktop + mobile. Кроме того, Vuetify DataTable/TreeTable-сценарии менее подходят для учетной нагрузки CollegePortal.

### Последствия

Нужно:

- подготовить план интеграции Quasar без создания нового проекта;
- сохранить существующий API-клиент или аккуратно адаптировать его;
- не менять backend и базу данных при GUI-рефакторинге;
- переносить интерфейс поэтапно, начиная с каркаса, layout, auth и пилотного раздела `Студенты`;
- использовать Tailwind только как слой кастомизации и фирменного стиля, а не как замену компонентам Quasar;
- использовать Lucide Icons как основной icon set;
- не подключать PrimeFlex, чтобы не смешивать две utility CSS-системы.

### Риски

- Quasar требует изучения своих patterns и может сильнее влиять на структуру frontend, чем обычная компонентная библиотека.
- Для сложных TreeTable-сценариев Quasar слабее PrimeVue; если ФРДО/ФИС-модули реально потребуют TreeTable, решение можно принять отдельно для конкретного экрана.
- Нужна аккуратная интеграция с текущим Vite-проектом, чтобы не создать новый проект и не сломать рабочий frontend.

### Проверки после внедрения

- frontend собирается через `npm run build`;
- backend не менялся;
- текущие API endpoints работают;
- вход/выход работают;
- раздел `Студенты` работает как пилотный модуль;
- таблицы, формы, фильтры, импорт/экспорт и карточка студента работают;
- интерфейс остается плотным и рабочим, близким по подходу к 1С-Колледж.
## ADR-002: архитектура подсистемы «Приемная комиссия»

Дата: 2026-07-24

Статус: принято для ADM-001 architecture foundation.

Решение: выделить «Приемную комиссию» как отдельный модуль домена `Administration`, связанный с `Person`, `Academic`, `Reference Data`, `Audit`, `RBAC`, `Dashboard` и отдельным integration layer ФИС.

Подробно: `docs/adr/ADR-002_ПРИЕМНАЯ_КОМИССИЯ.md`.
## ADR-003: модель данных подсистемы «Приемная комиссия»

Дата: 2026-07-24

Статус: принято для ADM-002 data model foundation.

Решение: использовать нормализованную модель данных с `Person`, `Applicant`, `Application`, выбранными специальностями, документами, достижениями, экзаменами, конкурсами, приказами, зачислениями, статусами и справочниками. Приказ и зачисление отделены от статуса заявления, а ФИС остается интеграционным снимком данных.

Подробно: `docs/adr/ADR-003_МОДЕЛЬ_ДАННЫХ_ПРИЕМНОЙ_КОМИССИИ.md`.
## ADR-004: API подсистемы «Приемная комиссия»

Дата: 2026-07-24

Статус: принято для ADM-003 API and process foundation.

Решение: использовать REST API с отдельными областями applicants, applications, choices, documents, competitions, orders, enrollments, FIS packages, reference и events. Критичные операции оформляются отдельными командными endpoints с RBAC, Audit, подтверждением и preview/apply там, где есть массовый или юридический эффект.

Подробно: `docs/adr/ADR-004_API_ПРИЕМНОЙ_КОМИССИИ.md`.
## ADR-005: стратегия реализации подсистемы «Приемная комиссия»

Дата: 2026-07-24

Статус: принято для ADM-004 implementation strategy foundation.

Решение: реализовывать подсистему эволюционно через небольшие backend/frontend/test задачи и layered architecture: Frontend Workspace -> API Controllers -> Application Use Cases -> Domain Services -> Repositories -> Database/Private Storage/Audit/Reference Data. Текущий `/admissions` сохраняется до завершения миграций, backfill и smoke.

Подробно: `docs/adr/ADR-005_СТРАТЕГИЯ_РЕАЛИЗАЦИИ.md`.
