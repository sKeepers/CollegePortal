# Проходная и сканирование QR-пропусков

## Назначение

Модуль проходной регистрирует вход и выход по цифровым QR-пропускам CollegePortal. MVP использует таблицу `digital_identities` из QR-001 и создает журнал событий в `access_events`.

## Рабочий сценарий

1. Сотрудник проходной открывает `/access/gate`.
2. Курсор автоматически находится в поле сканирования.
3. USB QR-сканер работает как HID-клавиатура и вводит токен из QR.
4. После Enter frontend отправляет `POST /api/access/scan`.
5. Backend проверяет токен и создает событие прохода.
6. Интерфейс показывает крупный результат: разрешено или отказано.

## QR и безопасность

QR-код содержит только технический `token` цифрового пропуска. В QR не записываются:

- ФИО;
- email;
- телефон;
- группа;
- роль;
- другие персональные данные.

Персональные данные подтягиваются сервером только после авторизованного API-запроса сотрудника.

## Таблица access_events

Поля:

- `id`;
- `digital_identity_id` - ссылка на цифровой пропуск, nullable для неизвестных токенов;
- `entity_type` - `student` или `teacher`, nullable для неизвестных токенов;
- `entity_id`;
- `direction` - `in` или `out`;
- `event_time`;
- `access_point`;
- `device_name`;
- `result` - `allowed` или `denied`;
- `reason`;
- `created_at`, `updated_at`.

## API

### POST /api/access/scan

Тело запроса:

```json
{
  "token": "uuid-or-random-token",
  "access_point": "Главный вход",
  "device_name": "HID QR Scanner"
}
```

Логика:

- если токен найден и пропуск активен, создается `allowed`;
- если пропуск не найден, отозван, приостановлен или истек, создается `denied`;
- направление определяется автоматически: если последнее событие было `in`, новое будет `out`, иначе `in`.

### GET /api/access/events

Возвращает последние события проходной, включая владельца пропуска, результат и направление.

## Frontend

Страница: `/access/gate`.

Интерфейс содержит:

- большое поле сканирования с автофокусом;
- настройки точки доступа и имени устройства;
- крупный результат последнего сканирования;
- фото-заглушку владельца;
- ФИО, тип владельца, направление, время;
- список последних событий.

## Ограничения MVP

- Поддерживаются только студенты и преподаватели.
- Фото владельца пока отображается как заглушка.
- Нет отдельной роли охраны, используется существующее право `manage_dictionaries`.
- Нет отдельной проверки расписания или рабочего времени.

## Следующие этапы

- Отдельная роль `security` / `access_operator`.
- Фильтры журнала событий по дате, владельцу, результату и точке доступа.
- Отчеты по входам и выходам.
- Связь с расписанием и опозданиями.
- Поддержка NFC/RFID без изменения общей модели событий.
