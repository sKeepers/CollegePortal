# План: авторизация и мобильный контур

Дата: 07.08.2026.
Ветка планирования: `feature/uat-002-1-final-stabilization` (`6b19fe4`).

Документ описывает две запрошенные владельцем системы линии работ: расширение способов входа и мобильный контур для пяти ролей. Это план, а не отчёт о реализации.

## Часть 1. Авторизация

### Текущее состояние

Проверено по коду на `6b19fe4`:

- единственный способ входа — логин и пароль, далее bearer-токен;
- идентификатором служит email, `username` или телефон связанного `Person`/`Student`/`Teacher`;
- токен: `Str::random(80)`, хранится как bcrypt-хеш и индексированный SHA-256 lookup hash, TTL 720 минут;
- ограничение частоты: вход 5/мин на пару IP+email, защищённый API 120/мин на пользователя;
- на клиенте токен лежит в `localStorage` или `sessionStorage` по выбору пользователя;
- **сброса пароля нет**: ни маршрута, ни контроллера;
- **смены пароля нет**: пользователь не может сменить пароль сам;
- **внешних провайдеров нет**;
- почтового транспорта фактически нет: `config/mail.php` присутствует, но в проекте ноль `Mailable` и ноль `Notification`.

### AUTH-001: Смена пароля в личном кабинете

**Зависимости:** нет. Можно начинать немедленно.

**Объём:** защищённый `POST /api/auth/password` с текущим и новым паролем; единое правило пароля, общее с административным созданием учётных записей; отзыв прочих активных токенов пользователя; запись в audit без значения пароля; раздел «Безопасность» в личном кабинете, доступный всем ролям.

**Критерии готовности:** неверный текущий пароль возвращает 422 без раскрытия деталей; после смены прежний токен недействителен; правило пароля совпадает с `AdminUserController` и installer; в audit нет ни старого, ни нового значения; есть позитивные и негативные тесты.

**Связь:** пересекается с `SEC-007` в части единой password policy — выполнять согласованно, не вводя две разные политики.

### AUTH-002: Восстановление пароля

**Зависимости:** рабочий транспорт почты. Требуется решение владельца системы: SMTP-сервер колледжа, адрес отправителя и допустимость отправки писем с ПДн.

**Нерешённый вопрос, который нельзя угадывать в коде:** у части студентов может не быть личного email. Возможные пути:

1. восстановление по email — стандартный путь Laravel, дешевле всего;
2. восстановление по телефону через SMS — требует провайдера, договора и бюджета;
3. восстановление администратором — уже работает через `POST /api/admin/users/provision` с одноразовой карточкой.

**Рекомендация:** реализовать путь 1, сохранив путь 3 как основной для пользователей без email. Путь 2 выносить отдельной задачей только при наличии SMS-провайдера.

**Критерии готовности:** токен восстановления одноразовый и с ограниченным TTL; ответ не раскрывает, существует ли адрес; действует rate limit; после сброса отзываются активные токены; письмо не содержит лишних ПДн; есть тесты на истёкший, повторно использованный и чужой токен.

### AUTH-005: Общий слой внешних провайдеров

**Зависимости:** согласовать с `SEC-002` (модель сессии), так как callback провайдера должен выдавать тот же артефакт аутентификации, что и обычный вход.

**Выполнять до AUTH-003 и AUTH-004**, иначе Telegram и MAX будут написаны двумя несовместимыми способами.

**Объём:** таблица связей `user_identities` (`user_id`, `provider`, `provider_user_id`, `linked_at`) с уникальностью пары провайдер+идентификатор; интерфейс провайдера; экран «Способы входа» в личном кабинете с привязкой и отвязкой; audit привязки и отвязки.

**Критерии готовности:** один внешний аккаунт нельзя привязать к двум учётным записям; отвязка доступна пользователю и администратору; отвязка последнего способа входа не оставляет учётную запись без пароля.

### AUTH-003: Вход через Telegram

**Зависимости:** `SEC-004` и `AUTH-005`. Telegram Login Widget требует привязки **публичного домена** к боту — на IP-адресе и самоподписанном сертификате он не работает. Проверять придётся на PROD `https://portal.skki.ru`: DEV живёт на `https://192.168.34.114:5443` и для виджета непригоден. `SEC-004` выполнен, ограничение снимается после установки на PROD релиза с новым шаблоном nginx.

**Объём:** бот, Login Widget, серверная проверка поля `hash` как HMAC-SHA256 по строке проверки данных с ключом из токена бота, контроль давности `auth_date`, привязка к существующему пользователю.

**Ключевое требование безопасности:** вход через мессенджер **только привязывается к уже существующей учётной записи** и никогда не создаёт новую. Иначе любой владелец Telegram-аккаунта получит доступ к порталу. Привязка выполняется из личного кабинета уже вошедшим пользователем с подтверждением текущим паролем.

**Критерии готовности:** через Telegram невозможно создать учётную запись; подделанная или просроченная подпись отклоняется; привязка и вход пишутся в audit; токен бота не попадает во frontend, в git и в логи; есть тесты на корректную подпись, подделанную подпись, просроченный `auth_date` и попытку привязать уже занятый Telegram ID.

### AUTH-004: Вход через MAX

**Зависимости:** `SEC-004`, `AUTH-005`.

**Первый шаг задачи — проверка, а не реализация:** подтвердить наличие официального публичного API авторизации MAX для сторонних систем, его условия использования и требования к регистрации приложения. Ссылку на официальную спецификацию зафиксировать в задаче. Не проектировать интеграцию по аналогии с Telegram без подтверждённой документации.

**Объём и критерии:** те же, что у `AUTH-003`, через общий интерфейс провайдера из `AUTH-005`, плюс документированный источник спецификации.

### Рекомендуемый порядок

`AUTH-001` → `AUTH-002` → `AUTH-005` → `AUTH-003` → `AUTH-004`.

`AUTH-001` даёт пользу сразу и ни от чего не зависит. `AUTH-003` и `AUTH-004` бессмысленно начинать до доверенного TLS.

## Часть 2. Мобильный контур

### Текущее состояние

- `frontend/src/services/layoutService.js` даёт пять профилей устройств: `phone` (<600), `tablet` (<1200), `desktop-hd` (<1920), `desktop-fullhd` (<2560), `desktop-ultrawide` (>=2560);
- реализован мобильный кабинет **студента**: `MobileStudentLayout`, маршруты `/mobile/student/*`, страницы главной и QR-пропуска, permissions `mobile.student.view` и `mobile.student.pass`;
- реализован `MobileScannerPage` для проходной;
- ручная проверка на реальных устройствах в журналах проекта не зафиксирована.

Роль `curator` («Куратор группы») **уже существует** в `RoleSeeder` с правами преподавателя плюс `students.view`, `groups.view` и `attendance.reports`; у групп есть привязка куратора.

### MOB-001: Мобильный кабинет преподавателя

**Зависимости:** нет.

**Объём:** свои занятия на сегодня и неделю, открытие журнала занятия, отметка посещаемости и выставление оценок в один экран без горизонтальной прокрутки, свой QR-пропуск. Без редактора расписания и без административных действий.

**Критерии готовности:** преподаватель видит только свои занятия; отметка посещаемости работает одной рукой на телефоне; недоступные действия скрыты, а не выдают ошибку; есть permission `mobile.teacher.view`.

### MOB-002: Мобильный кабинет куратора

**Зависимости:** `MOB-001` — переиспользует те же компоненты.

**Объём:** закреплённая группа, посещаемость группы за день и неделю, список студентов с контактами, отчёты проходной по своей группе.

**Критерии готовности:** куратор видит только закреплённые за ним группы; доступ к чужой группе по подстановке ID запрещён и покрыт тестом; есть permission `mobile.curator.view`.

### MOB-003: Мобильное рабочее место проходной

**Зависимости:** `SEC-004`, выполнен. Доступ к камере требует доверенного secure context; на самоподписанном сертификате мобильный браузер камеру не даст. Проверять на телефоне по адресу `https://portal.skki.ru` после установки релиза на PROD. `Permissions-Policy` в шаблоне nginx оставляет `camera=(self)` — если заголовок когда-нибудь ужесточат, сканер перестанет работать.

**Объём:** доработка существующего `MobileScannerPage`: компактный режим, низкая нагрузка, устойчивость к потере фокуса и блокировке экрана, понятная индикация результата, ручной ввод как запасной путь.

**Критерии готовности:** непрерывное сканирование не роняет вкладку; результат виден без вглядывания; работает нормализация русской раскладки для HID-сканера (уже реализована в `fix/access-qr-keyboard-layout`); проверено на реальном телефоне по доверенному HTTPS.

### MOB-004: Мобильный кабинет администратора

**Зависимости:** нет.

**Объём:** ключевые показатели рабочего стола, входящие уведомления и запросы на переоткрытие журнала с возможностью решения, поиск человека, быстрый доступ к карточке.

**Критерии готовности:** решение по запросу редактирования журнала выполняется с телефона полностью; список входящих совпадает с desktop-версией; есть permission `mobile.admin.view`.

### MOB-005: PWA-упаковка

**Зависимости:** `SEC-004` (установка PWA требует доверенного HTTPS), выполнен, и `SEC-002` (модель сессии определяет поведение при офлайне), остаётся открытым.

**Объём:** service worker, доведение существующего `frontend/public/manifest.webmanifest`, иконки, офлайн-заглушка, экран установки.

**Рекомендация:** именно PWA, а не нативное приложение. Кодовая база одна, магазины приложений не нужны, Quasar это поддерживает. Нативную обёртку через Capacitor добавлять позже и только если понадобятся push-уведомления.

**Критерии готовности:** приложение устанавливается на Android и iOS; при потере сети показывается понятное состояние, а не белый экран; версия и build видны в интерфейсе.

### Рекомендуемый порядок

`MOB-001` → `MOB-002` → `MOB-004` → релиз на PROD → `MOB-003` → `MOB-005`.

Три кабинета не зависят ни от чего и делаются сразу. Проходная и PWA упирались в доверенный TLS; теперь — в установку релиза, в котором он включён.
